# Design Note: Release 2D.1 — Calendar

**Status:** Completed and merged to main as PR #35 at merge commit `85f692b`

**Updated:** September 22, 2026

**Context:** Phase 2D (Planning and Templates), Release 2D.1 (ROADMAP §7)

---

## 1. Outcome and non-goals

A dedicated `/calendar` page shows task due dates and milestone due dates for the current workspace in a **month** or **week** view. It has project, assignee, status and kind filters, an **unscheduled-work panel**, **drag-to-reschedule with explicit Save / Cancel**, visible error recovery, and a keyboard-accessible date editor.

**Non-goals:** external calendar sync (iCal, Google), recurring tasks, timeline/Gantt, reminders, notifications scheduled by date, automation jobs, start dates or durations, time-of-day scheduling.

**No migration.** The calendar reuses `task.due_date` and `milestone.due_date` in both databases. Existing indexes already support the reads: PostgreSQL `task_workspace_due_idx (workspace_id, due_date)` and `milestone_workspace_due_idx (workspace_id, due_date)`, and SQLite `tasks_due_idx` and `milestones_due_idx`.

---

## 2. The date rule (one rule, everywhere)

**A task or milestone due date is a date-only value. Its calendar day is the UTC calendar date of the stored value.**

| Stored value | Calendar day |
|---|---|
| SQLite `"2026-10-01"` (what the UI has always written) | `2026-10-01` |
| PostgreSQL `2026-10-01 00:00:00` (`new Date("2026-10-01")`, read as UTC) | `2026-10-01` |
| Any legacy full timestamp, such as `"2026-10-01T23:30:00-05:00"` | its UTC date: `2026-10-02` |

This is the rule the codebase already uses: the task board's date inputs (`dueDate.slice(0, 10)`), the activity log's `task.dates_changed` comparison (`toISOString().slice(0, 10)`), and 2C.6's `toDateOnly`. **Existing dates are not reinterpreted or migrated.** A calendar day is never computed in the browser's or the server's local zone, so a server in UTC and a browser in `Pacific/Auckland` or `America/Los_Angeles` place an item on the same day.

**Writes.** Rescheduling sends `"YYYY-MM-DD"` through the existing routes, so SQLite stores that string and PostgreSQL stores UTC midnight, exactly as the task and milestone forms already do. A legacy value with a time component becomes date-only when the user moves it; that is an explicit user action, not a silent migration.

**Browser time zone.** The browser's IANA zone, from `Intl.DateTimeFormat().resolvedOptions().timeZone`, decides only what **today** is: the highlighted cell, the Today button, and the overdue marker. The page shows the zone it is using. The API accepts an optional `tz` and returns `today` computed in that zone, so client and server agree.

**Supported calendar: 1900-01-01 to 9999-12-31, inclusive.** Grids are clamped to it: December 9999 ends on Friday 9999-12-31, and the week containing it has five days. Previous and Next are disabled when the whole adjacent period would fall outside it. Range queries ending on 9999-12-31 work in both databases. PostgreSQL bounds the range with SQL `date`s (`< to::date + 1`), which can express 10000-01-01. SQLite's lexical prefilter caps its upper bound, because `"10000-…"` sorts before `"9999-…"` as text.

**Grid arithmetic.** Month and week grids are pure `YYYY-MM-DD` arithmetic using `Date.UTC`, and never local `Date` objects. UTC has no daylight-saving time, so a DST transition in the browser cannot duplicate, skip or shift a day. Weeks start on **Monday (ISO 8601)**, regardless of locale. A month grid is the Monday on or before the 1st through the Sunday on or after the last day: 4 to 6 weeks.

**Display.** Day numbers and month names are formatted with `timeZone: "UTC"` from the date-only value, so the label cannot shift a day in any zone.

## 3. API

All routes are `Cache-Control: no-store`. Repeated query parameters are rejected with 400.

### `GET /api/calendar`

| Param | Rule |
|---|---|
| `from`, `to` | required, strict `YYYY-MM-DD`, real calendar dates (for example `2028-02-29` is valid and `2026-02-29` is not), years 1900–9999, `from ≤ to`, inclusive span ≤ **42 days** (the largest month grid) |
| `projectId` | optional; must be a project in the current workspace |
| `assignee` | optional: `me`, `unassigned`, or a user id with a membership row in the current workspace. **Accounts mode only**; 400 on desktop. When set, milestones are excluded because they have no assignee. |
| `status` | `all` (default), `open` (todo + in_progress), `todo`, `in_progress`, `done`, `cancelled`. Applies to tasks. Milestones follow it as `open` → open, `done` → completed, `cancelled` → cancelled, `todo`/`in_progress` → open. |
| `kind` | `all` (default), `tasks`, `milestones` |
| `tz` | optional IANA zone (≤ 64 characters, accepted by `Intl.DateTimeFormat`), used only for `today` |

Response: `{ workspaceId, from, to, today, timeZone, items: CalendarItem[], truncated, canReschedule }`. Each `CalendarItem` is `{ kind, id, title, date: "YYYY-MM-DD", projectId, projectName, status, assigneeId? }`. Items are ordered by date, then kind, then title, then id. The result is capped at **1,000** items; `truncated: true` tells the UI to ask for narrower filters.

### `GET /api/calendar/unscheduled`

Tasks with no due date, filtered by `projectId`, `assignee` and `status` as above. `limit` is 1–50 (default 25). A strict opaque `cursor` over `(created_at, id)` gives stable **Load more** paging. Response: `{ workspaceId, items, nextCursor }`. Milestones without a date are not listed; see §9.

### `GET /api/calendar/filters`

Response: `{ workspaceId, projects: [{id, name}], projectsTruncated, projectLimit, members: [{id, name}], membersTruncated, memberLimit, canReschedule }`. Members are **active** members, returning `id` and `name` only (never email, image, role or status). The two lists have **independent** caps of 500 each (`MAX_FILTER_PROJECTS`, `MAX_FILTER_MEMBERS`). Each is read with `limit + 1`, so `projectsTruncated` and `membersTruncated` are true exactly when more exist. On desktop `members` is empty.

When a list is truncated, the page says so. The select keeps the first 500, and a **Search projects** or **Search members** box beside it reaches every other value (below). A value picked through search stays visible in its select even though it isn't in the first page. Small workspaces keep plain selects, with no search box and no notice. The notice is about the option list only. It does not claim every project's items appear, because the calendar result has its own 1,000-item cap.

### `GET /api/calendar/filters/search?type=projects|members&q=&limit=&cursor=`

A bounded name search for filter values beyond the initial lists:

- **Scope:** the caller's current workspace, in SQL. Any active role may search, including viewers, who remain read-only. Member search exists in accounts mode only; on desktop, `type=members` is 400.
- **Matching:** `q` is trimmed, at most 100 characters, with no control characters. It is a case-insensitive substring of the **name only**, never email, so a search cannot probe for addresses. `%`, `_` and `\` match literally.
- **Rows:** members are **active** only; suspended, removed and invited members never appear.
- **Response:** `{ workspaceId, type, q, results: [{ id, name }], nextCursor }`. It carries `id` and `name` only.
- **Paging:** `limit` is 1–50 (default 25), keyset-paged over `(lower(name), id)` with a strict opaque cursor, so every matching row is reachable with **More matches** while each response stays bounded.
- **Why not the existing directory APIs:** `GET /api/workspaces/[id]/members` returns email, image, role, status and joinedAt, which the calendar must never receive. `GET /api/projects` returns full project records. This endpoint follows the same workspace-scoping and strict-validation rules with a minimal payload.

**Client behavior:** searches are debounced (300 ms) or sent immediately on Enter; Enter on the query already searched sends nothing. Requests belong to a *generation*. Editing the text, starting a search, changing workspace or unmounting starts a new one: it aborts the in-flight request (first page or "More matches"), cancels the pending debounce and drops the results on screen immediately, so results for text the box no longer contains are never shown, selectable or appended. A response, error or `finally` from an older generation changes nothing, so a stale request cannot end a newer request's loading state. Responses must also carry the expected `workspaceId` and query, and the view is keyed by workspace. The search shows accessible states: idle hint, searching, no matches, error with Retry search, and "more matches".

**Selection is still validated.** A picked id is sent as `projectId` or `assignee` to `/api/calendar`, which re-validates it against the workspace. Foreign and unknown ids get the same generic `400 Unknown filter value.`

### Rescheduling uses existing routes

- Task: `PATCH /api/tasks/:id` with `{ dueDate }`
- Milestone: `PATCH /api/projects/:projectId/milestones/:milestoneId` with `{ dueDate }`

These routes already apply the `member` role check, workspace scoping, 404 for foreign or unknown ids, activity events, and 2C.6 due-date notifications. The calendar adds no new write path.

## 4. Repository contract

A new `CalendarRepository`, with implementations `PostgresCalendarRepository` and `DrizzleCalendarRepository`, is chosen in the composition root exactly like the others. SQLite is `require`d only when `DATABASE_URL` is absent.

- `listRange(workspaceId, range, filters, limit)` runs exactly **two queries** (tasks and milestones), each joined to `project` for the name, never one query per item.
  - **PostgreSQL:** `workspace_id = $ws AND due_date >= from AND due_date < to + 1 day`, which uses the `(workspace_id, due_date)` indexes. The project join is also constrained to the same workspace.
  - **SQLite:** asserts `LOCAL_WORKSPACE_ID`. An index-friendly prefilter, `due_date >= from − 1 day AND due_date < to + 2 days` (lexical), absorbs any UTC offset of ±14 hours. It is followed by the exact rule `date(due_date) BETWEEN from AND to`; SQLite's `date()` converts offsets to UTC, which matches §2.
- `listUnscheduled(workspaceId, filters, cursor, limit)` runs one keyset query `ORDER BY created_at, id`, fetching `limit + 1` rows.
- `projectExists(workspaceId, projectId)` and `memberExists(workspaceId, userId)` validate filter ids, scoped in SQL.
- `listFilterOptions(workspaceId)` returns projects and active members (id and name only).

## 5. Authorization and isolation

| Caller | Read calendar | Reschedule |
|---|---|---|
| Owner / Admin / Member | ✓ | ✓ (via existing routes) |
| Viewer | ✓ (`canReschedule: false`; no drag or edit controls rendered) | 403 from existing routes |
| Suspended / removed, cookie naming that workspace | 403 | 403 / 404 |
| Outsider | only their own workspaces | 404 |
| Unauthenticated (accounts mode) | 401 | 401 |

Every read is scoped by `workspace_id` in SQL. **Unknown and foreign filter ids return the same 400 `Unknown filter value.`**, so the response never reveals whether a project or user exists elsewhere. Foreign task or milestone ids on the write routes return the existing 404. Accounts mode is PostgreSQL-only; the calendar never imports the SQLite client there, and the fresh-process no-SQLite test covers the new routes and page.

## 6. Interaction model

1. The user **drags** an item, from a day cell or from the unscheduled panel, onto a day.
2. The UI shows a **pending change**: the item appears on the target day marked "Pending", and a status bar reads "Move *Title* from Oct 1 to Oct 4 — Save / Cancel". Nothing is sent to the server.
3. **Cancel** discards the overlay. The item never left its confirmed date.
4. **Save** calls the route for the item's kind. While in flight, Save, Cancel, dragging, the reschedule buttons, navigation and filters are **disabled**, so the same item cannot be saved twice and the view cannot change underneath the save.
5. **Success** applies the date the server just confirmed, clears the pending state, then refreshes the visible range and the unscheduled panel in place. The item never flashes back to its old day while the refresh is in flight.
6. **Failure** clears the pending overlay, so the item is back on its last confirmed date. A `role="alert"` message shows the server's error, with **Retry** (re-applies and saves the same change) and **Dismiss**.

Only **one** pending change exists at a time. Dragging another item while one is pending is refused, and the status bar says so. Navigation and filter changes while a change is pending but not yet saved are allowed; the pending bar stays visible, because it holds its own copy of the item.

**Keyboard alternative:** every item has a **Reschedule** button that opens a dialog with a native date input, **Save** and **Cancel**. It goes through the same save pipeline and error handling. Escape closes the dialog and returns focus to the button. Drag-and-drop is never the only way to reschedule.

**Workspace switching:** the page is keyed by workspace id, and every response carries `workspaceId`. A response for any other workspace is discarded, so a switch cannot flash another workspace's items. The accounts-mode workspace selector on the page switches via the existing `PUT /api/workspaces/current`.

**States:** loading (`aria-busy` with text), empty ("Nothing scheduled in this range"), error with Retry, truncated notice, unscheduled Load more and end-of-list.

---

## 7. Desktop

The calendar is available on desktop, backed by SQLite only. The assignee filter is hidden and rejected by the API, because desktop has no users. Rescheduling uses the same existing task and milestone routes.

## 8. Performance

Each view reads only the visible grid (≤ 42 days), in two indexed queries capped at 1,000 items. The unscheduled panel pages 25 at a time. Filter options are two bounded queries. The browser never receives the whole workspace. Tests seed thousands of rows and assert that only in-range rows come back.

## 9. Known limitations

- Unscheduled milestones are not listed in the panel; milestones are rescheduled from the grid or from the project board.
- No clear-date action on the calendar. Clearing a due date stays on the task board.
- Items beyond the 1,000 cap in one range are not shown; the UI says so and suggests filters.
- The existing task board's `formatDate` renders date-only values in the browser's local zone, so it can display one day early west of UTC. It was left unchanged here to keep this release scoped; the calendar uses the rule in §2.
