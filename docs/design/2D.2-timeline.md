# Design Note: Release 2D.2 — Timeline

**Status:** Implemented on `phase2d/timeline`, uncommitted, awaiting independent review

**Updated:** September 24, 2026

**Context:** Phase 2D (Planning and Templates), Release 2D.2 (ROADMAP §7). Builds on Release 2D.1 — Calendar (`docs/design/2D.1-calendar.md`).

---

## 1. Outcome and non-goals

A read-only **project timeline** at `/projects/[id]/timeline` shows, for one project in the current workspace:

- tasks and milestones placed on their dated day across a **week**, **month** or **quarter** window, with Previous, Next and Today navigation;
- **dependency connectors** between visible tasks;
- **blocked** tasks and the **blocking path** — the dependency chain responsible for the block;
- **date conflicts** the existing data can prove (§6);
- an **undated and partially dated** section, so no work is silently hidden;
- an **accessible table** carrying the same information as the graphical view.

**Non-goals (this release):** editing of any kind (drag, resize, inline date changes), start dates, durations, schedule-critical-path analysis, baselines, resource levelling, exports, and a cross-project (portfolio) timeline.

## 2. Data model decisions

**Task ranges with the current schema.** Neither database has a task start date. `task.due_date` (SQLite `tasks.due_date`) is the only planning date; `created_at` is creation time, not planned start time, and is never used to invent a range. **A task is therefore a dated point — its due day — not a bar.**

**Is a new nullable start date required?** No, not for this release. Everything the roadmap asks of a *read-only* timeline — seeing when work lands, dependency lines, blocked-path highlighting, conflicts, zoom and navigation — is deliverable truthfully from due dates and dependencies. A start date would touch both schemas, the task API and forms, bulk editing, activity history and the Calendar, for a view that cannot yet edit it. It is deferred to the editing follow-up (§12), where ranges become meaningful because users can set them. The limitation is stated in the UI ("Read-only. Tasks are shown on their due date; start dates are not recorded yet.") and here. **No migration; both Drizzle generators remain no-ops.**

**Milestones** are **dated points** (`milestone.due_date`), drawn as a diamond. They are not ranges: nothing records when a milestone starts.

**Undated and partially dated work.** Nothing is hidden:

| Case | Where it appears |
|---|---|
| Task with a due date in the window | On the grid and in the table |
| Task with a due date outside the window | Not on this window's grid; it appears when navigated to. It is still named wherever it blocks, or is blocked by, a visible task (§5) |
| Task with **no** due date, whose milestone **has** a date (*partially dated*) | Undated section, labelled "No due date — milestone target YYYY-MM-DD" |
| Task with no due date and no dated milestone (*undated*) | Undated section, "No due date" |
| Milestone with no target date | Undated section, "Milestone — no target date" |

A task whose start is after its due date cannot exist: there is no start date. When start dates arrive, the server will reject `start > due` (§12).

## 3. Date and time-zone rules

The Timeline reuses `src/core/calendar/dates.ts` — no second date implementation:

- every day is a strict `YYYY-MM-DD` string; arithmetic goes through `Date.UTC`, so no zone or daylight-saving transition can duplicate, skip or shift a day;
- a stored due date's day is its UTC calendar date (`calendarDayOf`), exactly as on the Calendar;
- the supported calendar is `1900-01-01` … `9999-12-31`; windows are clamped, and Previous/Next are disabled when the adjacent window lies wholly outside it;
- the browser's IANA zone is used for one thing only: what *today* is (`todayInTimeZone`), computed in the browser exactly as on the Calendar. It drives the Today marker, the default window and "overdue". The client also sends `tz`; the server validates it and reports `today` for that zone for API consumers.

**Windows** (new, in `src/core/timeline/range.ts`) are derived on the server from `zoom` + `anchor`, so the browser never supplies an arbitrary range:

| Zoom | Window | Grid unit |
|---|---|---|
| `week` | The ISO week (Mon–Sun) containing the anchor | day |
| `month` | Full ISO weeks covering the anchor's month (≤ 42 days) — the Calendar's `monthRange` | day |
| `quarter` | Full ISO weeks covering the anchor's calendar quarter (≤ 105 days) | day, labelled by week |

`MAX_TIMELINE_DAYS = 105` bounds every window.

## 4. API and repository

`GET /api/projects/[id]/timeline?zoom=week|month|quarter&anchor=YYYY-MM-DD[&tz=Area/City]`

- **Authorization** reuses `resolveCalendarContext` (Release 2D.1): desktop → the local workspace; accounts mode → 401 without a session, 403 when the workspace cookie names a membership that is suspended or removed, otherwise any **active** role (owner, admin, member, viewer). The workspace comes from the server-side session and cookie resolution — never from a query parameter.
- **Project scope:** the project must exist **in the resolved workspace**. A project id that is malformed, nonexistent or in another workspace returns the same `404 {"error":"Project not found"}` — the existing project-route convention.
- **Strict query parsing:** only `zoom`, `anchor` and `tz`; repeated or unknown parameters → 400; `anchor` strict `YYYY-MM-DD` inside the supported calendar; `tz` a validated IANA name.
- `Cache-Control: no-store` on every response.
- Read-only: the route exposes no write, and the page renders no editing controls for any role.

**Repository** (`TimelineRepository`, PostgreSQL and SQLite). One `load(workspaceId, projectId, range, limits)` call issues a small fixed set of list queries plus a dependency walk whose statement and row counts are bounded by constants (§7) — never one query per item:

1. the project (id, name) scoped by workspace;
2. tasks due in the window (`limit + 1`), with milestone title/date joined within the same workspace;
3. milestones due in the window (`limit + 1`);
4. undated tasks (`limit + 1`) and undated milestones (`limit + 1`);
5. **exact `blocked`** for every returned task — one statement computing a linear closure over the tasks reachable from the returned tasks (§6, §7), guarded by a reachable-task cap and, on PostgreSQL, a statement timeout;
6. the **explanation graph** — a bounded breadth-first walk from the returned tasks (`exploreDependencies`, §7): at most 1,000 dependency rows kept, per-task `LIMIT`ed primary-key range scans, 50 tasks per statement, at most 32 levels;
7. id, title, status, due day and project name for explanation-graph endpoints not already returned (blockers outside the window or in another project of the same workspace), one query bounded by the edge cap.

In accounts mode the route then resolves assignee **names only** (`getMemberDisplaySummaries`, projected to `{ id, name }` — never email, image or role). Desktop has no users and sends no assignees.

PostgreSQL scopes every query, CTE seed, recursive step, task lookup and project lookup by `workspace_id` and, where relevant, `project_id`; every join repeats the workspace condition. The whole read runs in one `READ ONLY` transaction with `SET LOCAL statement_timeout`. SQLite asserts `LOCAL_WORKSPACE_ID`, like every Drizzle repository.

**Payload** — only what the Timeline renders: item kind, id, title, status, due day, milestone id/title/day, assignee id, `blocked`, immediate blockers, blocking path and whether that explanation is complete, conflicts; the dependency edges; referenced external nodes (id, title, status, day, project name); window, `today`, limits and truncation flags. No descriptions, comments, files, emails, authentication fields or credentials.

## 5. Dependency lines

Edges are `task → depends on` from `task_dependency`. Dependencies may cross projects within a workspace (the existing routes allow it), so:

- a **connector** is drawn only when **both** endpoints are on the current grid (drawn from the blocker's marker to the dependent's marker, in an SVG overlay with `pointer-events: none` that can be hidden);
- an edge to a task **off the grid** (another window, undated, or another project) is never drawn; it is **named** instead — in the item's tooltip text, the table's "Immediate blockers" column and the blocking-path text — with its day and, if external, its project;
- the explanation graph holds at most `MAX_TIMELINE_EDGES` edges (§7). When the walk stops early the response says `truncated.edges: true`, each affected task carries `blocking.complete: false`, and the page says the explanation is incomplete. `blocked` stays exact because it never comes from the explanation graph.

## 6. Blocking path (not "critical path")

**Formal critical-path analysis needs durations; this product has none.** The feature is called **blocking path** in the UI and in this note, and makes no schedule-criticality claim.

Definitions, reusing the existing invariant (`docs/ROADMAP.md` hardening; the task repositories' `loadBlockedSet`):

- **Resolved** = `done` or `cancelled`. **Unfinished** = anything else.
- A task is **blocked** iff **any** task reachable from it along dependency edges is unfinished. Traversal passes *through* resolved tasks, so a completed task cannot conceal an unfinished transitive blocker. The timeline computes this exactly with its own statement — a linear closure (below) rather than `loadBlockedSet`'s per-root traversal, whose `(root, task)` pairs multiply with a shared graph — and tests assert it equals the task repositories' `blocked` for every returned task, on both databases.
- The **blocking roots** of a blocked task are the unfinished tasks reachable from it.
- The **blocking path** is the union of breadth-first shortest paths from the task to each blocking root. Neighbours are visited in a fixed order — due day ascending (undated last), then title, then id — so the path is deterministic when several exist; with multiple branches, every branch that reaches an unfinished task is included. A visited set makes cycles harmless (the repository already rejects them) and traversal is bounded by the loaded edges.
- **Immediate blockers** are the direct dependencies that lie on the blocking path — the next task(s) to look at.

**Exact blocked state.** `reach` = the tasks reachable from the returned tasks (each enters the recursion once); `blocked` = the tasks in that region with an unfinished direct dependency, closed backwards over dependency edges within the region (each enters once). A task is in the closure iff it reaches an unfinished task — the canonical definition — and both recursions deduplicate, so cycles terminate. If more than `MAX_TIMELINE_ANALYSIS_TASKS` tasks are reachable, or PostgreSQL's statement timeout fires, the route answers `503 {"error":"This project's dependency graph is too large to analyse right now."}` (no SQL details, retryable) instead of guessing.

**Explanations.** Roots, path and immediate blockers are computed from the bounded explanation graph. When it is complete for a task, "has at least one blocking root" equals `blocked`; tests assert this parity. When it is not (`blocking.complete: false`), roots and path may be partial or empty, the UI says the explanation is incomplete, and `blocked` is still exact — a task is never shown as unblocked because the explanation was cut off.

**Date conflicts** (proved from existing data only):

- **Due before its blocker** — an unfinished task is due strictly earlier than an unfinished direct dependency's due day.
- **Due after its milestone** — an unfinished task is due strictly later than its milestone's target day.

**Overdue** — an unfinished item whose day is before the browser's *today* (§3).

## 7. Limits and workload

| Limit | Value |
|---|---|
| Window | ≤ 105 days (`MAX_TIMELINE_DAYS`) |
| Dated tasks per window | 400 (`MAX_TIMELINE_TASKS`) |
| Dated milestones per window | 100 (`MAX_TIMELINE_MILESTONES`) |
| Undated tasks / undated milestones | 200 / 50 |
| Explanation graph edges | 1,000 (`MAX_TIMELINE_EDGES`) |
| Tasks per exploration statement / levels | 50 (`TIMELINE_EXPLORE_BATCH`) / 32 (`MAX_TIMELINE_DEPTH`) |
| Reachable tasks for the exact blocked analysis | 50,000 (`MAX_TIMELINE_ANALYSIS_TASKS`) |
| PostgreSQL statement timeout (whole read) | 3,000 ms (`TIMELINE_STATEMENT_TIMEOUT_MS`) |
| Connectors drawn | only edges with both endpoints on the grid (≤ edge cap) |

Each list is read with `limit + 1` so truncation is reported truthfully (`truncated.tasks`, `.milestones`, `.undatedTasks`, `.undatedMilestones`, `.edges`), with guidance to switch to a narrower zoom. Items are ordered deterministically: day, milestones before tasks, title, id (the Calendar's order); undated tasks by milestone target day (none last), title, id.

**Why the explanation graph is genuinely bounded.** The walk (`src/core/timeline/explore.ts`) asks each statement for at most 50 tasks' dependencies and at most `remaining + 1` rows per task, each an ordered, `LIMIT`ed range scan of the `(task_id, depends_on_task_id)` primary key — so the database never reads more than that per task, whatever the task's fan-out. A statement whose rows all fit the budget is consumed completely, so all such statements together read at most 1,000 rows; the first statement that does not fit ends the walk and read at most 50 × 1,001 rows. At most 32 levels are walked. Hence, for any graph:

- rows read by the walk ≤ 1,000 + 50 × 1,001 = 51,050;
- walk statements ≤ ⌈returned tasks / 50⌉ + ⌈1,000 / 50⌉ + 32 ≤ 64.

A visited set makes cycles terminate; frontiers and each task's dependencies are ordered by id, so the output is deterministic. On PostgreSQL the `LIMIT` follows the database's collation order and on SQLite its binary order, so when a single task's dependencies are cut off the particular subset kept can differ between databases; the contract (≤ 1,000 edges, truncation reported, `complete` flags, exact `blocked`) is the same.

**Why exact blocked state is bounded.** Its closure is linear in the reachable region, not multiplicative: each reachable task enters `reach` once and each blocked task enters `blocked` once. PostgreSQL cannot `LIMIT` a recursive term, so it is guarded by the reachable-task cap (checked on the result) and the statement timeout (which bounds the work itself); a timeout becomes the generic 503. SQLite has no statement timeout, so its recursive step carries `LIMIT 50,001`, which bounds how many reachable tasks it will ever enqueue; more than 50,000 is refused the same way. The backward step reads each blocked task's dependents through the `depends_on` index — on SQLite that is at most the local database's dependency rows, each at most once.

## 8. Desktop and hosted accounts

Both modes use the same route, page and component. Desktop (SQLite) has one local workspace, no users and no assignee column in the output; accounts mode (PostgreSQL) scopes by the resolved workspace and shows assignee names. No Electron IPC or desktop privilege change.

## 9. Viewer permissions

Every active role, including **viewer**, can read the Timeline. Nothing on the page edits data for anyone in this release; item names link to the existing task board and milestone views, which enforce their own permissions.

## 10. Client behaviour

- The view is keyed by workspace and project; each load has a sequence number and an `AbortController`. Changing zoom or navigating aborts the previous request, and a response is applied only if it matches the latest request's workspace, project, zoom and anchor — so neither rapid navigation nor a workspace switch can show stale data.
- States: loading, empty window (undated work still listed), error with Retry (including the 503 when the dependency graph is too large to analyse), truncated notices, and "project not available" for a 404 (a foreign, deleted or inaccessible project).
- Layout: a fixed label column and a horizontally scrolling date grid, so small screens scroll the grid rather than squashing it.

## 11. Accessibility

- Status is never colour alone: each item carries a text/icon label — "Done ✓", "Cancelled" (struck through), "Blocked", "Overdue", "Open" — and conflicts are written out.
- Item names are real links (keyboard reachable); markers are decorative (`aria-hidden`) with the same facts in text.
- Dependency connectors are decorative and can be hidden; the **table** below the chart lists name, type, project, due/target day, status, assignee (accounts mode), blocked state, immediate blockers and the blocking path as text. It is the complete, CSS-independent representation.
- No raw HTML from user data; all text renders through React. Links are built from validated ids with `encodeURIComponent`.

## 12. Deferred editing

Deferred to the follow-up release: drag to move, resize, start dates (added deliberately to both schemas, the task API, forms, bulk edits and activity history, with server-side `start ≤ due`), conflict resolution actions, and durations. Until then the Timeline is strictly read-only.
