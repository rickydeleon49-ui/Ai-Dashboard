# Design Note: Release 2C.3 — Task Checklists

**Status:** Approved for Implementation (Stage 3A)  
**Author:** AI-Dashboard Engineering Team  
**Updated:** September 19, 2026  
**Context:** Phase 2C (Team Collaboration), Release 2C.3 (ROADMAP §6)

---

## 1. User Outcome & Non-Goals

### User Outcome
In both hosted accounts mode (`AUTH_MODE=accounts`) and desktop mode (SQLite), tasks often consist of a sequence of actionable sub-steps that are too small to justify standalone child tasks.
Release 2C.3 introduces **task checklists**:
- Users can add, edit, reorder, complete (check), reopen (uncheck), and delete checklist items within any task.
- Users can optionally **convert a checklist item into a full task** in the same project when an item grows in scope.
- Checklist progress (e.g., `3/5` done) is surfaced on task cards and details views.
- In hosted accounts mode, item attribution (`created_by`, `done_by`, `done_at`) is captured with full tenant workspace isolation.

### Non-Goals for Release 2C.3
- **No Checklist Item Dependencies or Assignees:** Per ROADMAP §6, checklist items do not have their own assignees, due dates, milestones, or dependency graphs. Those belong exclusively to full tasks.
- **No Nested Checklists:** Checklists are a flat, ordered list per task. No multi-level hierarchies inside checklist items.
- **No Rich Markdown in Checklist Items:** Checklist item text is single-line, trimmed plain text (up to 500 characters).

## 2. Data Model: PostgreSQL & SQLite

### PostgreSQL Schema (`task_checklist_item`)
Additive table created via migration `drizzle-pg/0013_task_checklists.sql`:

```sql
CREATE TABLE "task_checklist_item" (
  "id" text PRIMARY KEY,
  "workspace_id" text NOT NULL REFERENCES "workspace"("id") ON DELETE CASCADE,
  "task_id" text NOT NULL REFERENCES "task"("id") ON DELETE CASCADE,
  "position" integer NOT NULL,
  "text" text NOT NULL,
  "done" boolean NOT NULL DEFAULT false,
  "done_by" text REFERENCES "user"("id") ON DELETE SET NULL,
  "done_at" timestamp,
  "created_by" text REFERENCES "user"("id") ON DELETE SET NULL,
  "created_at" timestamp NOT NULL DEFAULT now(),
  "updated_at" timestamp NOT NULL DEFAULT now()
);

CREATE INDEX "task_checklist_item_task_pos_idx" ON "task_checklist_item" ("task_id", "position");
CREATE INDEX "task_checklist_item_workspace_task_idx" ON "task_checklist_item" ("workspace_id", "task_id");
```

## 3. Ordering Strategy & Concurrency

### Dense Integer Positions (`0..N-1`)
Checklist items within a task use 0-indexed contiguous integer positions (`0, 1, 2, ...`):
1. **Creation:** A new item is assigned position `N` (where `N` is the current item count for that task).
2. **Deletion:** Remaining items with `position > deletedPosition` are shifted down by 1 (`position = position - 1`) to keep the sequence dense.
3. **Reordering (`reorder(workspaceId, taskId, itemIds)`):**
   - The caller supplies the complete ordered list of item IDs for the task.
   - Each item is assigned its new 0-indexed position: `position = index`.
   - Any ID not belonging to the task is rejected with HTTP 422.

### Concurrency Serialization
To prevent conflicting concurrent reorders or interleaved position writes:
- In PostgreSQL, mutations for a task lock the parent task row using `SELECT id FROM task WHERE id = :taskId AND workspace_id = :workspaceId FOR UPDATE` (or lock the checklist table rows for that task within a transaction).
- This ensures two concurrent reorders are strictly serialized: the first transaction establishes its order, and the second transaction executes sequentially on top of the committed state without creating duplicate or fragmented positions.

## 4. Convert Item to Task

When converting a checklist item to a task:
1. The repository loads the checklist item and verifies it belongs to `workspaceId` and `taskId`.
2. The parent task's `projectId` is retrieved.
3. A new task is created in the same project using the standard `taskRepository.create()` method:
   - `title`: `item.text`
   - `projectId`: parent task's `projectId`
   - `actorUserId`: authenticated caller
   - All standard task invariants (project existence, schema validation, actor attribution) are executed.
4. The checklist item is atomically deleted from `task_checklist_item` within the same transaction.
5. Remaining checklist items are re-indexed.
6. If task creation fails for any reason, the transaction rolls back completely, ensuring the checklist item is preserved.

## 5. Authorization & Roles

- **Accounts Mode (`AUTH_MODE=accounts`):**
  - Task checklist endpoints live under `/api/tasks/[id]/checklist`.
  - Routes enforce tenant workspace verification (`resolveWorkspaceAndUserForRequest`).
  - **Mutations (POST, PATCH, DELETE, reorder, convert):** Require role `member`, `admin`, or `owner` (`requireRole("member")`). Viewers are rejected with HTTP 403 `forbidden`.
  - **Reads (GET):** Viewers and active members can list checklist items.
  - **Suspended & Removed Members, Outsiders:** Denied access (403/404).
- **Desktop Mode:**
  - Single-user SQLite environment. All operations proceed without authentication. `created_by` and `done_by` are `null`.

---

## 6. Server-Side Limits & Validation

1. **Max Items Per Task:** Maximum **100** checklist items per task. Creating an item beyond 100 returns HTTP 422 (`ChecklistLimitExceededError`: "Task checklist cannot exceed 100 items").
2. **Text Constraints:**
   - Minimum: 1 character (after trimming whitespace). Empty or whitespace-only text returns HTTP 422.
   - Maximum: **500** characters. Exceeding 500 characters returns HTTP 422.
3. **Task Scope Verification:** Every checklist operation validates that `task_id` belongs to the acting `workspace_id`. Cross-workspace access returns HTTP 404 or fails to find rows.

## 7. Open Decisions from ROADMAP §20

1. **OPEN DECISION 1 — Activity Events for Checklist Changes:**
   - *Roadmap context:* ROADMAP §6 lists "Activity entries for meaningful checklist changes", while Release 2C.4 introduces the formal activity timeline and schema.
   - *Status:* **OPEN** (mirroring Release 2C.2). In Release 2C.3, durable attribution columns (`created_by`, `done_by`, `done_at`) are captured directly on the `task_checklist_item` row. Integration into the unified activity feed will take place in Release 2C.4.

2. **OPEN DECISION 2 — Completed Task Invariant with Incomplete Checklists:**
   - *Context:* Can a task be marked `done` while it still has incomplete checklist items?
   - *Decision:* Yes. Checklists serve as progress indicators and breakdown guides; they do not block top-level task completion (unlike formal task blocking dependencies).
