## 1. User Outcome & Non-Goals

### User Outcome
In both hosted accounts mode (`AUTH_MODE=accounts`) and desktop mode (SQLite), users managing projects or their own task list frequently need to triage, reassign, reschedule, or re-prioritize multiple tasks at once. Previously, this required clicking into every individual task.

Release 2C.5 introduces **safe, accessible bulk task editing**:
- **Task Selection in Project Views and My Work:** Interactive multi-task selection with keyboard support, individual checkboxes, select-all-visible toggling, and an active selection count badge.
- **Bulk Action Toolbar:** A responsive, accessible action bar allowing simultaneous or individual updates to `status`, `priority`, `milestone`, `dueDate`, and `assignee`.
- **Clear Value Operations:** Explicit capabilities to clear milestones (`milestoneId: null`), unassign tasks (`assigneeId: null`), and clear due dates (`dueDate: null`).
- **Truthful Partial-Failure Handling:** If some tasks fail (e.g. invalid milestone for a task's project, assignee not an active workspace member, or attempted completion of a blocked task), successful items are committed, failed items are reported with specific machine-readable error codes and human-readable explanations, and failed tasks are retained in the selection for immediate retry.
- **Confirmation for Potentially Disruptive Actions:** Prompting user confirmation when performing bulk cancellation, bulk completion, or bulk unassignment.

### Non-Goals
- **No Uncontrolled Client Loops:** Clients do not fire separate PATCH requests in a client loop. All bulk updates execute through a single dedicated endpoint (`POST /api/tasks/bulk`).
- **No Bulk Deletion:** Task deletion is not included in bulk operations. Destructive status changes (e.g. `cancelled`) follow existing task status rules with explicit confirmation.
- **No Client-Supplied Tenant or Actor Trust:** Workspace ID and acting user ID are never accepted from the request body; they are strictly derived from the authenticated session context.
- **No Unbounded All-or-Nothing Transactions:** Large bulk updates do not lock entire tables or abort 99 valid updates due to 1 invalid task. Instead, bounded per-task transactions provide atomic, independent execution with truthful partial-failure accounting.
- **No Task Labels in Release 2C.5:** See Section 16 below regarding the investigation and deferral of task labels.

## 2. Request and Response Contracts

### Endpoint
`POST /api/tasks/bulk`

### Request Shape
```json
{
  "taskIds": ["task_1", "task_2"],
  "changes": {
    "status": "in_progress",
    "priority": "high",
    "milestoneId": "ms_123",
    "assigneeId": "usr_456",
    "dueDate": "2026-10-15"
  }
}
```

#### Request Validation Rules
- `taskIds`: Array of strings, 1 to 100 items (`BULK_TASK_MAX_BATCH_SIZE = 100`). Each task ID must be between 1 and 200 characters and contain no newline or control characters. Duplicate IDs are deduplicated upfront (`requested` reflects unique task count).
- `changes`: Object containing at least one supported field (`status`, `priority`, `milestoneId`, `assigneeId`, `dueDate`). Empty change objects are rejected with `400 Bad Request`.
- Unknown fields on the request body or change object are strictly stripped/rejected via Zod schemas (`.strict()`).
- `dueDate` must be a valid ISO 8601 date string or `null`.
- `milestoneId` must be a valid string ID or `null`.
- `assigneeId` must be a valid string ID or `null`.

### Response Envelope
```json
{
  "requested": 2,
  "succeeded": 1,
  "updated": 1,
  "unchanged": 0,
  "failed": 1,
  "results": [
    {
      "taskId": "task_1",
      "status": "updated"
    },
    {
      "taskId": "task_2",
      "status": "failed",
      "errorCode": "blocked_task",
      "error": "Cannot mark task as done while it has incomplete dependencies.",
      "retryable": false
    }
  ]
}
```

Invariant: `requested === results.length === (updated + unchanged) + failed`.

Possible item `status` values:
- `"updated"`: The task was successfully modified and changes committed.
- `"unchanged"`: The request succeeded but all requested fields already matched existing task values (no database write or activity event emitted).
- `"failed"`: The task could not be updated. `errorCode`, `error`, and `retryable` are included. Unexpected runtime or database exceptions return `errorCode: "internal_error"` with `retryable: true` without aborting the batch or leaking internals.

## 3. Authorization & Tenant Scoping

### Server-Derived Context
The server resolves the active `workspaceId` and `userId` via `resolveWorkspaceAndUserForRequest(request)`. The client cannot pass or override `workspaceId` or `actorId`.

### Role Enforcement
- In hosted accounts mode (`AUTH_MODE=accounts`), the caller must be an authenticated member of the workspace with at least the `"member"` role (`requireRole(workspaceId, userId, "member")`).
- `"viewer"` callers are rejected with `403 Forbidden`.
- Callers who are not members or whose membership is suspended/removed are rejected with `403 Forbidden`.
- Unauthenticated callers are rejected with `401 Unauthorized`.
- In desktop mode (SQLite), authentication checks are bypassed and the local workspace context (`LOCAL_WORKSPACE_ID = "default"`) is used.

### Cross-Workspace Task Isolation
Every task ID in `taskIds` is loaded strictly scoped to `workspaceId`: `taskRepository.findById(workspaceId, taskId)`.
- If a task ID belongs to another workspace or does not exist, it fails with `errorCode: "not_found"` and error message `"Task not found."`.
- This ensures zero cross-tenant leakage: existence of tasks in other workspaces is never revealed.

---

## 4. Batch Limit & Transaction Boundaries

### Batch Size Enforcement
- Maximum batch size: **100 tasks** (`BULK_TASK_MAX_BATCH_SIZE = 100`).
- If `taskIds.length === 0`, rejected with `400 Bad Request` (`"At least one task ID is required."`).
- If `taskIds.length > 100`, rejected with `400 Bad Request` (`"Cannot update more than 100 tasks in a single request."`).

### Transaction Boundaries
- Bulk editing uses **bounded per-task transactions** rather than a single sprawling transaction covering all tasks.
- If task 1 succeeds, task 2 fails validation, and task 3 succeeds:
  - Task 1 is committed.
  - Task 2 is recorded as failed.
  - Task 3 is committed.
- This prevents a single invalid task or lock contention from blocking 99 valid updates.
- Tasks are only counted as `succeeded` after their respective transaction commits.

## 5. Invariant Enforcement & Error Codes

Each task is evaluated against all existing business domain invariants before modifying state:

| Error Code | HTTP Equiv | Cause | Retryable? |
|---|---|---|---|
| `not_found` | 404 | Task does not exist in the active workspace. | `false` |
| `invalid_milestone` | 400 | The specified milestone belongs to another project or workspace. | `false` |
| `invalid_assignee` | 400 | The specified assignee is not an active member of this workspace (suspended, removed, invited, or outsider). | `false` |
| `blocked_task` | 409 | Attempted to mark a task as `"done"` when dependencies are incomplete (`task.blocked === true`). | `false` |
| `validation_failed` | 400 | Task input data failed schema validation. | `false` |
| `conflict` | 409 | Concurrent write conflict or lock timeout. | `true` |
| `internal_error` | 500 | Unhandled database or operational exception. | `true` |

## 6. Activity Events & No-Op Suppression

### Attribution
- In hosted accounts mode, activity events are authored with `actorId: userId` (the authenticated user).
- Single-task parity is maintained: updates emit `task.updated` and `task.status_changed` / `task.assigned` as appropriate.

### No-Op Suppression
If a bulk request specifies `{ status: "todo", priority: "medium" }`, but a task already has `status: "todo"` and `priority: "medium"`:
- The item is returned with `status: "unchanged"`.
- No database write is performed for that task.
- No redundant activity event is published.
- Re-executing the same bulk update produces zero noise in project activity feeds.

---

## 7. Desktop vs. Hosted Parity

- **Desktop SQLite Mode:** Uses `DrizzleTaskRepository` and SQLite storage. Assignee fields are ignored or nullified as desktop mode has no user accounts. Milestone, status, priority, and due date bulk operations work identically.
- **Hosted Accounts Mode (PostgreSQL):** Uses `PostgresTaskRepository` and PostgreSQL storage. Full tenant isolation, membership validation, assignee resolution, and activity event logging are strictly enforced.

---

## 8. Multi-Project My Work Behavior

Tasks displayed in the "My Work" view can span multiple projects within the same workspace.

### Milestone Bulk Editing Decision:
- **Project Views:** All visible tasks share the same project; milestones belonging to that project are freely selectable.
- **My Work View:**
  - If the user selects tasks that **all share a single project**, that project's milestones are dynamically fetched and enabled in the milestone selector.
  - If the user selects tasks that **span multiple different projects**, the milestone selector disables setting a project milestone and displays `"(Multiple projects selected)"`.
  - However, **clearing milestones** (`"Clear milestone"`) remains enabled even when multiple projects are selected, as clearing is valid across all projects.
  - Furthermore, the server independently validates `milestone.projectId === task.projectId` for every task to guarantee that cross-project milestones can never be assigned even if requested directly via API.

## 9. Accessibility (a11y) & Responsiveness

- **Checkbox Labels:** All task checkboxes include descriptive accessible labels (`aria-label="Select task <Title>"` and `aria-label="Select all visible tasks"`).
- **Indeterminate State:** The "Select all visible" checkbox accurately sets `el.indeterminate` when some, but not all, visible tasks are selected.
- **Keyboard Navigation:** Selection checkboxes and toolbar dropdowns are standard HTML form elements fully navigable via `Tab` and `Space`/`Enter`.
- **Screen Reader Announcements:** The selected count badge includes `aria-live="polite"`.
- **Responsive Layout:** The `BulkActionsBar` wraps controls smoothly and avoids horizontal viewport overflow on narrow (mobile/tablet) viewports.

## 10. Task-Label Investigation & Deferral Decision

The prompt required investigating whether a workspace-scoped task-label model exists before attempting to implement bulk labeling.

### Investigation Findings
- Inspection of `src/db/schema.sqlite.ts` and `src/db/schema.pg.ts` revealed tables `tags` and `project_tags`.
- Both tables are joined strictly to `projects.id` (`project_id`).
- There is **no table or schema** for `task_tags`, `task_labels`, or task-level tagging in either SQLite or PostgreSQL.
- Tasks only possess `id`, `workspace_id`, `project_id`, `milestone_id`, `title`, `description`, `status`, `priority`, `due_date`, `position`, `assignee_id`, `assigned_by`, and timestamps.

### Deferral Decision
Per instructions: *"If only project tags exist and tasks do not have a label domain, do not misuse project tags or silently invent an incomplete label system. Document task labels as an explicit deferred dependency and explain what schema/API work a future focused release requires."*

### Future Work Required for Task Labels
A dedicated future release (e.g. Phase 2C.6 or 2D) should introduce:
1. `task_label` table: `id`, `workspace_id`, `name`, `color`, `created_at`.
2. `task_label_assignment` join table: `task_id`, `label_id`, `workspace_id`.
3. Migration scripts for both PostgreSQL (`drizzle-pg/`) and SQLite (`drizzle/`).
4. `TaskLabelRepository` with CRUD and bulk assignment methods.
5. REST API routes for label management (`/api/workspaces/:id/labels`).
6. UI components for label badges, color pickers, and filter pills.

---

## 11. Known Limitations
- Bulk editing supports up to 100 tasks per batch. Selections exceeding 100 must be partitioned into multiple batches.
- Subtask parent/child relationships cannot be bulk-reassigned (subtask hierarchies remain managed individually to preserve DAG integrity).
- Milestone assignment across multi-project selections requires selecting tasks from one project at a time or clearing milestones.
