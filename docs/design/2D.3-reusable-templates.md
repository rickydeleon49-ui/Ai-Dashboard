# Design Note: Release 2D.3 — Reusable Templates

**Status:** Implemented on `phase2d/templates`; independent review and local release verification complete, pending required GitHub checks and merge

**Updated:** September 30, 2026

**Context:** Phase 2D (Planning and Templates), Release 2D.3 (ROADMAP §7). Builds on 2D.1 Calendar (date-only rules) and 2D.2 Timeline.

---

## 1. Outcome and non-goals

Users define a **project template** — project defaults, milestones, tasks with one-level subtasks, task dependencies, task checklists and flat knowledge documents, all dated relative to a project start — then **preview** the project it would create for a chosen start date, and **apply** it to create the complete project in one atomic, retry-safe operation. It works on desktop (SQLite, no account, offline) and in hosted accounts mode (PostgreSQL, one workspace per template).

**Non-goals (this release):** public or cross-workspace sharing, import/export, template versions/history, "create template from an existing project", assignees or placeholder roles, task start dates or durations, uploaded-file templates, cloning comments/activity/notifications, GitHub or deployment configuration, secrets or credentials, recurring or background application, AI-generated templates, drag-and-drop editing, tags on template projects. See §15 for future work.

## 2. Data model

Normalized, template-owned tables in both databases (no free-form JSON document). Every child row belongs to exactly one template and is deleted with it (`ON DELETE CASCADE`). Items inside a template refer to each other through **template-local keys**, never database ids.

| Table | Purpose | Key columns |
|---|---|---|
| `project_template` | Metadata and project defaults | `id`; PostgreSQL: `workspace_id`, `created_by` (→ user, `SET NULL`); `name`, `description`, `project_name`, `project_description`, `project_type`, `project_status`, `created_at`, `updated_at` |
| `project_template_milestone` | Milestone templates | `(template_id, key)` unique; `position`, `title`, `description`, `target_offset` |
| `project_template_task` | Task and subtask templates | `(template_id, key)` unique; `position`, `title`, `description`, `priority`, `due_offset`, `milestone_key`, `parent_key` |
| `project_template_dependency` | Dependency edges | PK `(template_id, task_key, depends_on_key)` |
| `project_template_checklist_item` | Checklist items | `(template_id, task_key, position)`; `text` |
| `project_template_document` | Knowledge documents | `(template_id, position)`; `title`, `content`, `category`, `pinned` |
| `project_template_application` | Idempotency record for each application | unique `(workspace_id, actor_key, idempotency_key)`; `request_hash`; PostgreSQL: `template_id` + `template_workspace_id` (→ template, `SET NULL`), `project_id` + `project_workspace_id` (→ project, `SET NULL`) |

**Local references are enforced by the database, not only the app:** composite foreign keys tie `(template_id, milestone_key)` → milestone `(template_id, key)`, `(template_id, parent_key)` → task `(template_id, key)`, and dependency and checklist `(template_id, task_key)` → task `(template_id, key)`. A key can therefore only name an item **of the same template**. Keys match `^[a-z0-9][a-z0-9_-]{0,39}$` and are never interpreted as database ids — application always mints fresh ids — so a template cannot reference a live task, milestone, project, user or document anywhere.

Milestones, tasks, checklist items and documents keep their stored order (`position`). Dependencies are a set: they are returned in a fixed `(task_key, depends_on_key)` order.

PostgreSQL: every template table carries `workspace_id` (→ workspace, `CASCADE`), and every query filters on it. **The database also enforces workspace consistency:** `project_template` is unique on `(id, workspace_id)`, and every child row references its template through `(template_id, workspace_id)`; the nested keys above are `(template_id, workspace_id, …key)` → `(template_id, workspace_id, key)`, so no row can claim a workspace other than its template's. Application links use their own nullable `template_workspace_id` / `project_workspace_id` (a composite `SET NULL` clears every referencing column, which cannot include the `NOT NULL` `workspace_id`); checks require each to be null together with its id or equal to `workspace_id`, and `project` gains a unique `(id, workspace_id)` as the target. SQLite: single local workspace, no `workspace_id` column (repositories assert `LOCAL_WORKSPACE_ID`, like every Drizzle repository) and no user columns at all — desktop templates never depend on hosted user ids.

## 3. Ownership and visibility

- **Desktop:** templates are personal to the installation. SQLite only; available offline and without an account.
- **Hosted:** a template belongs to exactly one workspace and is visible to that workspace's active members only. The workspace is always resolved server-side from the session and the active-workspace cookie (`resolveWorkspaceAndUserForRequest`); no request body or query parameter can name a workspace (unknown fields are rejected). A template id from another workspace is indistinguishable from a nonexistent one: `404 {"error":"Template not found"}`.

## 4. Authorization matrix (hosted)

Derived from existing policy: projects are created, edited and deleted with the **member** role (`/api/projects`, `/api/projects/[id]`); every active role may read workspace planning data.

| Action | owner | admin | member | viewer | suspended / removed | unauthenticated |
|---|---|---|---|---|---|---|
| List / read template | ✔ | ✔ | ✔ | ✔ | 403 | 401 |
| Preview (no writes) | ✔ | ✔ | ✔ | ✔ | 403 | 401 |
| Create / edit / delete template | ✔ | ✔ | ✔ | 403 | 403 | 401 |
| Apply (creates a project) | ✔ | ✔ | ✔ | 403 | 403 | 401 |

Enforced on the server in every route (`requireRole`); application **re-checks the membership inside its transaction** with `SELECT … FOR SHARE` on the member row — before anything else, including returning an existing application for a retried key — so a suspension or role change that commits first wins and a member who lost access cannot replay a key to learn the project. A suspended/removed member whose cookie names the workspace gets 403 (no silent fallback), matching the Calendar/Timeline convention. The UI hides editing and apply controls for viewers, but that is presentation only. Desktop: the single local user may do everything.

## 5. Relative dates

- The user supplies a **project start date** (strict `YYYY-MM-DD`, validated by `isDateOnly`, 1900-01-01…9999-12-31).
- Milestone `target_offset` and task `due_offset` are **integer day offsets** in `0…3650` (≈ 10 years), or null for "no date". **Negative offsets are not supported** in this release (rejected at save).
- A date is `addDays(start, offset)` from `src/core/calendar/dates.ts` — `Date.UTC` arithmetic, no local time, so no zone or daylight-saving transition can shift a day. Leap days and month/year boundaries fall out of the same arithmetic (tested).
- A calculated date outside the supported calendar (e.g. start 9999-06-01 + 365) is a **validation error** in preview and application; nothing is written.
- Due dates are stored exactly as the task and milestone routes store them (date-only in SQLite, UTC midnight in PostgreSQL). No start dates or durations are invented.

## 6. Contents copied and never copied

| Item | Copied | Initial state on application |
|---|---|---|
| Project | name (overridable at apply), description, type (any project type), status (`idea`, `planning` or `active` — a new project is never created completed or archived) | `source = "manual"`, not favourite, not archived, empty metadata |
| Milestone | title, description, relative target date, order | `status = "open"` |
| Task | title, description, priority, relative due date, milestone and parent by local key, order | `status = "todo"`, unassigned, not blocked except by its template dependencies |
| Dependency | edge between local task keys | same direction as `task_dependency` ("task depends on") |
| Checklist item | text, order | not done, no actor, no timestamp |
| Knowledge document | title, content, category, pinned, order | new document |

**Never copied or stored:** ids of projects, tasks, milestones, documents or users; workspace ids from a client; assignees; GitHub/integration identifiers; repository or project URLs; local filesystem paths; project notes; uploaded files; credentials, tokens, secrets; deployment or automation settings; billing data; comments, activity, notifications; completion state or actors; original creators.

**Assignees:** templates store none; every created task is unassigned. Placeholder roles are future work (§15).

## 7. Validation (`src/core/templates/validate.ts`)

One pure validator runs at save, at preview and — on the data read inside the transaction — at application:

- strict schema: unknown fields rejected; strings trimmed and length-capped; enumerated statuses/priorities; offsets integers in range;
- keys unique per kind; every `milestoneKey`, `parentKey`, dependency endpoint and checklist `taskKey` resolves inside the template;
- **one-level subtasks:** a parent must be a top-level task, never itself; a task with children cannot be a subtask;
- **dependencies:** no self-edges, no duplicates (rejected), no missing endpoints, and **no cycles** — detected with an iterative Kahn topological sort (no recursion, O(tasks + edges));
- workload limits (§11).

## 8. Preview

`GET /api/templates/[id]/preview?startDate=YYYY-MM-DD[&name=…]` — strict parameters, `no-store`, read-only (no writes, no transaction side effects). The server recomputes everything: resulting project name, start date, each milestone's target date, each task's due date, the task hierarchy, dependency edges (by title), checklist counts, the document list, total records to be created, validation errors and warnings (e.g. "tasks are created unassigned"). Bounded by the template limits; contains no emails, roles, user ids, sessions or other-workspace data.

## 9. Atomic application

`POST /api/templates/[id]/apply` with `{ idempotencyKey, startDate, name? }`.

1. Validate the request (strict) and authorize (`member`), outside any transaction.
2. Open **one transaction** — PostgreSQL `db.transaction` (READ COMMITTED), SQLite `better-sqlite3` `db.transaction` (synchronous, so no other write can interleave).
3. PostgreSQL: re-check the caller's membership with `FOR SHARE` (active owner, admin or member; otherwise `forbidden`).
4. Look up the key: an existing application answers now (replay or conflict, §10) — only after step 3.
5. Lock the template `FOR SHARE` and insert the `project_template_application` row (with `project_id` null) — the idempotency claim (§10).
6. Read the template and all children **inside the transaction**, scoped to the workspace; re-run the validator and compute all dates. Any error aborts before a single project row exists.
7. Insert, in order: project; milestones; top-level tasks, then subtasks; dependencies; checklist items; knowledge documents; one `project.created` activity event (`metadata: { source: "template", templateId, templateName }`); then set the application's `project_id`.
8. Commit. Any exception rolls back everything, including the application row, so a failed attempt never consumes its key.

Ids are minted per item; the response maps template-local keys to the created ids deterministically (`{ project, milestones: {key: id}, tasks: {key: id} }`). No network calls happen inside the transaction. Activity: one project-level event only — no per-task `task.created` or checklist events (a template can create hundreds of rows; the project event plus the application record identify the origin without an activity storm).

## 10. Idempotency and retry

- The client generates a key (`^[A-Za-z0-9_-]{16,100}$`) when the user opens the apply step and reuses it for every retry of the **same** inputs; changing the template, start date or name produces a new key.
- Scope: unique `(workspace_id, actor_key, idempotency_key)`; `actor_key` is the user id in hosted mode and `"local"` on desktop (SQLite: unique `(actor_key, idempotency_key)`).
- `request_hash` = SHA-256 of the canonical `{ templateId, startDate, name }`.
- Same key + same hash → `200` with the already-created project (no new rows). Same key + different hash → `409 {"error":"This request key was already used for a different request."}`. A key whose project was later deleted → `409` as well (the retry would otherwise silently recreate it).
- **Concurrency (PostgreSQL):** the application row is inserted first. A second transaction with the same key blocks on the unique index until the first commits, then fails with a unique violation; it rolls back and, in a new transaction that re-locks and re-checks the membership first, reads the committed row → `200` with that project, or `409` if its hash differs. If the first transaction rolls back, the second proceeds. No in-memory locks.
- Failed transactions leave no application row, so the key stays usable.

## 11. Workload limits (`src/core/templates/limits.ts`)

| Limit | Value |
|---|---|
| Templates per workspace (desktop: per installation) | 200 |
| Milestones per template | 50 |
| Tasks per template (including subtasks) | 300 |
| Dependency edges per template | 600 |
| Checklist items per task / per template | 50 / 1,000 |
| Knowledge documents per template | 25 |
| Template / project / milestone / task / document title | 160 / 160 / 200 / 200 / 200 chars |
| Descriptions | 2,000 chars (template, project, milestone), 20,000 (task) |
| Checklist item text | 500 chars |
| Document content | 50,000 chars each, 500,000 total |
| Request body | 1 MB |
| Records created by one application | project + activity event + application record + items ≤ 3 + 50 + 300 + 600 + 1,000 + 25 = 1,978 |

All limits are checked before any transaction begins (and again on the data read inside it). Cycle detection is iterative and linear; no recursion depth depends on input.

## 12. API

| Route | Role | Notes |
|---|---|---|
| `GET /api/templates` | viewer+ | id, name, description, counts, `updatedAt` |
| `POST /api/templates` | member+ | full document (a name alone creates an empty template) → 201 |
| `GET /api/templates/[id]` | viewer+ | full document |
| `PUT /api/templates/[id]` | member+ | replaces the whole document atomically (children deleted and re-inserted in one transaction) |
| `DELETE /api/templates/[id]` | member+ | deletes the template and its children only |
| `GET /api/templates/[id]/preview` | viewer+ | §8 |
| `POST /api/templates/[id]/apply` | member+ | §9–§10 |

Strict parsing everywhere (unknown fields and query parameters, malformed ids, bad dates and offsets, unresolved keys, oversized content → 400 with a validation message; never database errors). Foreign or missing ids → the same generic 404. `Cache-Control: no-store` on every response.

## 13. Deletion

Deleting a template cascades to its own child rows only. Projects created from it are untouched; `project_template_application.template_id` becomes null (the application record stays so a retry of that key still returns its project). Deleting a created project sets the application's `project_id` null.

## 14. Migrations and rollback

Forward-only migrations generated with `npm run db:generate` / `db:generate:pg` (SQL, journal and snapshot together): SQLite `0010`, PostgreSQL `0016`. They only **add** tables, indexes and constraints; the one change to an existing table is PostgreSQL's unique `project (id, workspace_id)` (already implied by the primary key, so it cannot fail on existing rows). drizzle-kit emits that constraint last, after the foreign key that references it, so it was moved to the top of `0016` by hand (a statement-order change only; the snapshot is generated). Existing data is untouched and older application code ignores the new tables. Rollback: redeploy the previous release (it never reads these tables); to remove the feature's data, drop the seven `project_template*` tables in reverse dependency order, then the `project_id_workspace_uq` constraint. No destructive down-migration ships. Tested: fresh install, upgrade from the pre-template schema, and both generators being no-ops afterwards.

## 15. Future work

Create a template from an existing project; placeholder roles for assignees; negative offsets (pre-start planning); template tags and project tag defaults; version history; duplicate template; import/export within a workspace; applying into an existing project.

## 16. Desktop verification safety

The Electron shell suite relocates `app.getPath("userData")` before the single-instance lock or any profile access. Its bundled server, SQLite database, uploads, encryption key and window-state file therefore all use a fresh disposable directory. The suite reads back the actual main-process paths and fingerprints the installed profile before and after the run; it does not open, migrate, modify or clean up the installed database. Template application uses a fixed request key to prove fresh-profile isolation across repeated runs.

`DESKTOP_TEST_USER_DATA` is honored only by an unpackaged test launch and must be absolute. An unpackaged desktop test without that override refuses to start; ordinary development launches and packaged applications ignore the override. The test-path inspection hook is also unavailable in packaged applications.
