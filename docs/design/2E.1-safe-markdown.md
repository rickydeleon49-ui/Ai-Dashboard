# Design Note: Release 2E.1 — Safe Markdown

**Status:** Implemented on `phase2e/safe-markdown` (base `64481dd`, PR #38), with corrections for independent-review findings M1 (Markdown workload), M2 (legacy search indexing), C1 (underlines in containers and under CR/CRLF line endings), C2 (stale non-NULL search keys) and C3 (container prefixes inside indented nested-list content). Uncommitted, pending final review. Not merged.

**Updated:** September 30, 2026

**Context:** Phase 2E (Knowledge 2.0), Release 2E.1 (ROADMAP §8). Builds on the Release B knowledge base (`core/knowledge`, both knowledge repositories) and 2D.3 templates, which create knowledge documents.

---

## 1. Outcome and non-goals

Project knowledge documents are written, previewed and read as Markdown — headings, lists, tables, links, fenced code and task lists — identically in hosted accounts mode (PostgreSQL) and the offline desktop app (SQLite). The stored source is the Markdown exactly as typed; nothing converts existing documents. Search matches what a reader sees, not Markdown syntax or hidden link destinations.

**Non-goals (this release):** folders, revisions, attachments, workspace-wide search, Markdown in task comments, AI summaries, syntax highlighting, remote images or embeds of any kind, heading anchors/IDs, MDX or any content-selected component or plugin. Title, category, pinned behavior, the 50,000-character content limit and every permission rule are unchanged.

## 2. Rendering pipeline and dependencies

| Package | Version | Why |
|---|---|---|
| `react-markdown` | ^10.1.0 (installed 10.1.0) | Turns the Markdown tree into React elements directly. No HTML string, no `dangerouslySetInnerHTML`. Maintained (remarkjs). Security notes and options checked against the installed version's `readme.md` and `lib/index.js`. |
| `remark-gfm` | ^4.0.1 | Tables, task lists, strikethrough, autolinks, footnotes. |
| `remark-parse`, `unified` | ^11.0.0, ^11.0.5 | The same parser react-markdown uses (deduplicated: one `micromark`, one `unified` in the tree), driven directly for plain-text extraction so search reads the same tree that is rendered. |
| `@types/mdast` (dev) | ^4.0.4 | Types for the tree walk. |

There is **no HTML path**: no `rehype-raw`, so raw HTML never becomes elements. Because no step produces HTML, there is nothing for an HTML sanitizer to clean; safety is by construction, enforced by the allowlists below and verified in the browser. Next 16.3.3 needs no configuration for these ESM-only packages (App Router bundles them; Node 22+ `require(esm)` covers the tests).

One renderer, `components/knowledge/markdown-view.tsx` (`MarkdownView`), serves the editor's Preview tab, the new read-only document page and expanded list cards. It is not a Client Component — the document page renders it on the server; the client editor bundles it.

## 3. Rendering policy

- **Raw HTML** (`<script>`, `<img onerror>`, `<iframe>`, `<svg onload>`, comments, CDATA…) is shown **as literal text** (react-markdown's default with `skipHtml` off). It never becomes an element or attribute. Text *between* inline tags is ordinary text (CommonMark), shown and searchable like any other.
- **Element allowlist** (`allowedElements`): `p br hr h1–h6 blockquote ul ol li input pre code em strong del a img table thead tbody tr th td section sup`. Anything else is unwrapped to its text. `input` is admitted only as `type="checkbox"` and always renders `disabled readOnly` with an accessible label.
- **Headings** render one level down (`#` → `h2`): the page's `h1` is the document title.
- **Images never load.** `img` renders as `[Image: alt]` (`role="img"`, `aria-label="Image not loaded: …"`); `urlTransform` blanks every `src` as well.
- **Links** pass the URL policy (§4) in both `urlTransform` and the link component; a refused link renders as its text in a `span` with no `href`.
- **Tables** sit in a keyboard-focusable, horizontally scrolling region; **code blocks** scroll inside their own box; long words and URLs wrap (`overflow-wrap: anywhere`). Nothing widens the page (verified at 375 px).
- **Soft line breaks** display as line breaks (`white-space: pre-line` on text blocks) so documents written as plain text before this release keep their visible line structure.
- **Footnotes** use remark's `user-content-` id prefix (no DOM clobbering).
- The plugins and components are fixed in code; content cannot choose any of them.

## 4. URL policy (`core/knowledge/markdown-links.ts`)

`resolveMarkdownLink(raw)` returns `{kind, href}` or `null` (refused). Checks run on the destination after micromark has decoded character references, so `jav&#x61;script:` is seen as `javascript:`.

| Allowed | Rule | `href` produced |
|---|---|---|
| External | Literal `http://` or `https://` prefix, parses as a URL with that protocol, a non-empty host, **no username or password** | `URL.href` (normalized; IDN hosts in punycode) |
| Internal | Starts with exactly one `/`, resolves against a placeholder origin without leaving it | path + query + fragment |
| Anchor | Starts with `#` | unchanged |

Refused: every other scheme (`javascript:`, `data:`, `file:`, `vbscript:`, `mailto:`, `ftp:`, `ws:`, `blob:`, `about:`, `chrome:`…), protocol-relative `//host`, relative paths (`docs/x`, `./x`, `../x`), bare hosts, any **backslash** (`/\host`, `https:\\host`), any **whitespace** including Unicode spaces, ASCII/C1 **controls**, zero-width and bidirectional formatting characters, line/paragraph separators, the BOM, and anything over 2,048 characters. 37 refusal and 10 acceptance cases are unit-tested.

**External links** render `target="_blank" rel="noopener noreferrer nofollow ugc" referrerPolicy="no-referrer"`. In the browser test the new window has `window.opener === null` and an empty `document.referrer`.

**Electron:** unchanged. A `target="_blank"` link reaches `setWindowOpenHandler` in `desktop/main.js`, which hands only `http(s)` URLs to `shell.openExternal` and denies the window; an in-window navigation to another origin is stopped by `will-navigate` the same way. No IPC, preload or shell capability was added, and the launch secret is untouched. The desktop test stubs `shell.openExternal` and proves the external link reaches it, the app window does not navigate, no Electron window opens, and refused links reach nothing.

## 5. Limits and the complexity guard

| Limit | Value | Where |
|---|---|---|
| Content | 50,000 characters (unchanged; now one constant, `KNOWLEDGE_CONTENT_MAX`, shared by the API schema; templates use the same value) | `core/knowledge/markdown.ts`, `core/knowledge/schema.ts` |
| Container nesting per line (`>`, `-`/`+`/`*`, `1.`/`1)`, each after any spaces/tabs) | 100 | complexity guard |
| Emphasis/strike delimiter characters (`*`, `_`, `~`) | 4,000 per document | complexity guard |
| Closing brackets `]` (every link, image, reference, footnote and task-list candidate) | 2,000 per document | complexity guard |
| Setext underline candidates: lines whose content after any `>` / list prefixes is only `=` or only `-` (any indentation; thematic breaks, indented code and a bare `-` item included), with LF, CRLF and CR line endings | 500 per document | complexity guard |
| List-item markers in a line's leading container prefixes (`-`, `+`, `*`, `1.`–`123456789.`, `1)`; any indentation, nested lists' parents included) | 4,000 per document | complexity guard |
| Link destination | 2,048 characters | URL policy |
| Source parsed for a list summary | first 2,000 characters | `summarizeMarkdown` |
| List summary | 280 characters | `summarizeMarkdown` |

micromark is not linear for every input. Measured on the development machine at the 50,000-character limit with bounded subprocess diagnostics (each case in its own process with a hard timeout): nested `>` (50,000), `1. ` (16,666) or `*…a…*` inputs overflowed the call stack; 25,000 unmatched `*a` took ~3.5 s to parse plus ~4.5 s to render; nesting ≥ 2,000 took 0.3–0.8 s and crashed at ~4,000. **Review finding M1** showed the first guard missed other costly syntax: `"[a](".repeat(12499)` (49,996 characters) took ~1.8 s to parse. The follow-up diagnostics found the cost is in resolving closing brackets — `]` × 50,000 ≈ 7.4 s, `[a]` × 16,666 ≈ 3.5 s, `]]` × 25,000 ≈ 7.5 s, `[a]: ` × 10,000 ≈ 1.0 s — and in two further constructs: setext underlines (`a` / `=` repeated: ≈ 0.3 s at 2,000 pairs, ≈ 5.4 s at 8,000, ≈ 12 s at 12,500) and very long lists (12,500 one-character items ≈ 1.2 s to parse and ≈ 1.6 s to render). Plain `[`, `(`, `<`, backticks, entities, escapes, autolinks, tables and headings stayed below ~0.6 s at full size.

**Review finding C1** showed the underline count could still be bypassed by semantically equivalent syntax: the same headings inside a blockquote (`"> a\n> =\n".repeat(6000)`, 48,000 characters) or with CR-only line endings (`"a\r=\r".repeat(6000)`) passed the guard and took ~3 s each, because the line pass split only on LF and tested the raw line. The line pass now ends lines at LF, CRLF (one ending) or a lone CR, in any mix — exactly the line endings CommonMark recognizes — and tests for an underline in the content *after* the line's container prefixes (`>`, `-`/`+`/`*`, `1.`/`1)`, nested in any order). A bare `-` is consumed as a list marker but also counted as an underline, since under a paragraph it is one. The source is never normalized or rewritten to do this. The count is deliberately broader than CommonMark (an indented `===` code line counts); over-counting only chooses the plain-text fallback.

**Review finding C3** showed the prefix recognition itself was still too narrow: it applied CommonMark's *root-level* rule (a marker may be indented at most three spaces) to every physical line. Inside a nested list, four, eight or more spaces — or tabs — are the item's content indentation, and a real blockquote or list marker can follow. `- outer` / `  - inner` followed by 3,500 `    >a` / `    >=` pairs (49,018 characters) parsed into 3,500 headings (~1 s to parse, ~1.1 s to render) while the guard counted none; 6,000 `    + a` lines gave 6,002 list items; and `    ` + 101 × `> ` gave 101 quote levels. The pre-scan now recognizes container prefixes with a small manual scanner instead of an anchored regex: any run of spaces and tabs, then `>` (space optional), or `-`/`+`/`*`, or 1–9 digits then `.`/`)`, each list marker followed by a space, a tab or the end of the line — repeated, with the depth budget checked after every marker. Each character is examined at most once (a run of up to nine digits at most twice), so the scan stays linear; the underline test is a manual character check too, with no regular expression involved. Underlines are still tested after the prefixes, the bare-`-` rule still applies after indentation, and the real parser's grammar is untouched. The price is more false positives: because the pre-scan has no Markdown context, *any* indentation is treated as possible list content, so an indented code block whose lines start with `>`, `- `, `1. ` or `===` is counted as if it were containers or underlines. That can only choose the plain-text fallback, never hide or alter content.

`markdownComplexity()` is one linear, machine-independent pre-scan — a character pass and a line pass — that counts each budgeted construct and refuses a document over **any** budget **before** parsing. Renderer, editor preview, plain-text extraction, search indexing and summaries all take this one decision. A refused document (or any parser exception) is shown verbatim as preformatted text with a short notice, and its plain text for search is the source itself — so the decision is deterministic and nothing is hidden or rewritten. There is no timeout around parsing: synchronous parsing cannot be interrupted by a promise, so the guard prevents the work instead.

The budgets are conservative counts chosen from measured growth, **not a complexity proof**: they count characters anywhere (code blocks included), thematic breaks count as underlines, and a document past a budget for an innocent reason (a long code dump full of `snake_case`, more than 2,000 links or task items, a 4,000-item list) is shown as plain text. `tests/diagnostics/markdown-workload.tsx` (manual, not a test suite) reruns the diagnostics on the real guarded paths: with every budget at its limit and combined, and on budget-respecting fuzz, each step stayed under ~0.5 s on the development machine; one input type showed a ~1.2 s *first* parse in a cold process that fell to ~0.15 s warm (JIT warm-up, not input growth). Realistic documents stay well inside the guard: a 50,000-character document of headings, bold, links, lists, tables and code formats normally (unit-tested), as do references, footnotes, images, literal brackets (`array[0]`, `[not a link]`), Unicode and setext headings.

## 6. Plain-text extraction

`extractPlainText(source)` walks the same mdast tree: one line per block. Included: heading text, paragraphs, list and task-list item text, table cells (space-joined per row), fenced/indented code, inline code, link labels, image alt text and footnote definitions. Excluded: raw HTML markup nodes, link and image destinations, link-reference definitions (`[x]: url`), footnote reference markers and thematic breaks. Deterministic; empty/whitespace input yields `""`.

**List summaries** (`summarizeMarkdown()`, computed on the server for each card) bound their *input*, not just their output: only the first 2,000 characters of the source are parsed, after the full document's guard decision (a refused document is summarized from its raw prefix without parsing). A truncated summary ends in `…`. Truncation semantics: the summary reflects the start of the document only — a construct cut at the boundary contributes what it had so far (an unfinished link shows its label or literal brackets, never the rest of its destination; a reference defined later shows its bracketed label; an unclosed fence contributes code text), and a surrogate pair split at the boundary is dropped. The document page and search always use the whole document.

## 7. Search strategy

**A derived column**, populated by every writer, rather than parsing at query time:

- `search_text` = `normalizeForSearch(title + "\n" + category + "\n" + extractPlainText(content))`, where normalization is NFC → `toLowerCase()` → whitespace collapsed. One key covers title, category and visible text, so a single `LIKE` decides a match.
- Queries are normalized the same way and `%`, `_` and `\` are escaped (`ESCAPE '\'`), so `100%` and `snake_case` are literal. Both databases compare an already-lowercased key with an already-lowercased pattern, so SQLite (ASCII-only `lower`) and PostgreSQL (case-sensitive `LIKE`) match exactly the same documents, including non-ASCII text. A shared 22-query corpus asserts identical results on both backends.
- `search_indexed_at` records the `updated_at` the text was derived at. A row is **stale** when `search_text` is NULL or `search_indexed_at` differs from `updated_at` — every pre-2E.1 row, and any row an older build edits after a rollback (older builds always bump `updated_at`).
- **Writers:** `create` and `update` in both knowledge repositories and template application in both template repositories derive the text in the same statement. PostgreSQL `update` locks the row (`SELECT … FOR UPDATE` in a transaction) so concurrent partial updates cannot derive the key from a half-updated row (tested with concurrent title/content/category updates); SQLite's better-sqlite3 path is synchronous with no interleaving. PostgreSQL template rows use `now()`, equal to the `updated_at` default within the transaction, so they are fresh on arrival.
- **Backfill is a bounded, resumable batch per search (review finding M2).** The first version re-derived *every* stale row in a project on one search — 500 legacy rows in one request, even for a search with no results. Now each search request re-derives **at most one batch**: at most **25 rows** (`SEARCH_INDEX_BATCH_ROWS`) and at most **256 KiB** of stored title + category + content bytes (`SEARCH_INDEX_BATCH_BYTES`, measured by the database: `octet_length` / `length(CAST(… AS BLOB))`), always at least one row so progress is guaranteed (a maximum-size document fits in one batch). Candidates are taken in `id` order; only their ids and sizes are read until the batch is chosen, and only the chosen bodies are loaded. The batch is written in **one short transaction**. Progress is the rows themselves becoming fresh, so the next search resumes where the last stopped. Nothing loops batches to completion — not in a request, not at startup, not while a page renders — and plain listing never writes.
- **Search never presents incomplete results as complete.** `KnowledgeDocumentRepository.search()` (a separate operation; `list()` no longer accepts a search) returns `{ documents, index: { complete, pending, indexedNow } }`; `pending` is the number of stale documents left in the project after this request's batch. **Only fresh rows can match** (review finding C2): every result query requires a non-NULL `search_text` *and* `search_indexed_at` null-safely equal to `updated_at` (`IS` in SQLite, `IS NOT DISTINCT FROM` in PostgreSQL) — the exact complement of the staleness test. A stale key is not always NULL: an older build that edits a document changes its content and `updated_at` but leaves its previous `search_text`, which would otherwise keep matching words the document no longer contains (reproduced: a late-sorting row returned for a removed word until the third request). Stale rows therefore never appear in results, stay in the pending count and are re-derived by the normal batches; while `pending > 0` the result says so: the API adds `searchIndex: { complete, pending }` to search responses (plain listings are unchanged), and the knowledge page shows "Search is still indexing N older documents in this project, so these results may be missing matches" with a **Continue indexing** link that repeats the search (one more batch per visit). An incomplete search with no hits shows "No matches yet", never "No documents match". New and template-written documents are indexed immediately and are always searchable.
- **Concurrency.** PostgreSQL claims the batch with `SELECT … FOR UPDATE SKIP LOCKED`, so concurrent searches take different rows instead of redoing the same ones, and a row being edited (`update()` locks it) is skipped rather than waited for. SQLite runs the batch synchronously from first read to last write (better-sqlite3, no `await`), so searches in one process cannot interleave. Every refresh write remains conditional on title, category and content still matching what was read, touches only the two derived columns, and never changes `updated_at`, the source, pinning or order.
- **Category counts** for the filter are aggregated in the database (`categoryCounts()`, `GROUP BY`) instead of loading every document body.
- Workspace filtering is unchanged: every PostgreSQL query, including the refresh, filters on `workspace_id` and `project_id`. Listing selects explicit columns, so the derived text is never loaded outside search.

Search is still a per-project `LIKE` scan over the derived column (as before 2E.1 over the content); workspace-wide indexed search is Release 2E.4. A project with *N* stale documents becomes fully searchable after ⌈*N* / 25⌉ searches at most (fewer rows per batch when documents are large).

## 8. Editor and accessibility

- Write/Preview follows the WAI-ARIA tabs pattern: `tablist`/`tab`/`tabpanel`, `aria-selected`, roving `tabIndex`, ←/→/Home/End.
- The textarea has a real `<label for>` ("Content"), a described-by character counter (`n / 50,000`) and `aria-invalid` over the limit. It stays mounted (hidden in Preview), so switching tabs never loses text and the form still submits it. Preview renders only while open.
- The knowledge form's Title and Category inputs now have accessible names (the shared `Field` renders its label as a `span`; `Field` itself is unchanged).
- Save failures render in a `role="alert"` region with a status-specific message (401 session, 403 read-only, 404 gone, 422 validation, other statuses with the code, network failure) and always say the text is still there; nothing typed is cleared. Over-limit content is refused client-side before sending.

## 9. Permissions and isolation

- API authorization is unchanged: reads need membership; create/update/delete call `requireRole(…, "member")`. Viewers get `403`, content unchanged (API test and accounts browser test).
- Pages: a new read-only document page `/projects/:id/knowledge/:docId`. `resolveKnowledgePageAccess()` (presentation only) hides New/Edit/Delete/Pin for viewers in accounts mode; the new/edit pages show "Read-only access" to a viewer instead of a form. Desktop and single-user modes always write.
- A document reached through another project's URL is `notFound()` on both document pages. **Fixed in passing:** the edit page's `generateMetadata` put such a document's title in `<title>` even though the body was a 404; it now applies the same scoping (caught by the new accounts browser test).
- Accounts mode never touches legacy SQLite: membership comes from PostgreSQL via a dynamic import, and the three knowledge pages were added to `accounts-mode-no-sqlite`.
- `tests/unit-pg-auth/knowledge-workspace-scoping.test.ts` existed but was **not in the `test:unit:pg:auth` file list**, so it never ran in CI. It is now wired in (its six original tests pass unchanged).

## 10. Compatibility

- Existing documents are **not converted**: the stored source is unchanged and opens in the editor as written. Plain prose renders as paragraphs with its line breaks preserved.
- Plain text that happens to use Markdown syntax now formats: lines starting `#`, `-`, `1.`, `>` or four spaces, `*text*`/`_text_`, `` `code` ``, pipes forming a table. Runs of spaces collapse in prose. Text that looks like HTML is shown literally. In every case the source is intact and editable.
- Template documents are stored and applied unchanged and render like any other document.
- The search key ignores Markdown syntax and destinations, so a query containing `**` or a link URL no longer matches what it did before; visible text does.

## 11. Migration and rollback

| Database | Migration | Change |
|---|---|---|
| SQLite | `drizzle/0011_knowledge_search_text.sql` | `ALTER TABLE knowledge_documents ADD search_text text; ADD search_indexed_at text;` |
| PostgreSQL | `drizzle-pg/0017_knowledge_search_text.sql` | `ALTER TABLE knowledge_document ADD COLUMN search_text text; ADD COLUMN search_indexed_at timestamp;` |

Generated with `drizzle-kit generate` (both configs), journals and snapshots updated together; both generators are no-ops afterwards. Purely additive, nullable, no default: there is **no table rewrite and no data change**, and existing rows stay valid (they are re-derived in bounded batches by later searches, §7). It is not lock-free, though: `ALTER TABLE … ADD COLUMN` needs PostgreSQL's `ACCESS EXCLUSIVE` table lock (SQLite: the database write lock), so it waits behind long transactions on `knowledge_document` and blocks reads and writes of it while it waits. Apply it with the usual migration precautions — a quiet period or a `lock_timeout` with retry — rather than assuming it is instant.

**Rollback:** deploy the previous build; it ignores the columns, so **no schema change is needed to roll back** and the columns are left in place. Rows the older build edits become stale (it bumps `updated_at` without touching the derived columns) and are re-derived in bounded batches by later searches after roll-forward, with searches reporting them as pending until then. Removing the columns is never required; if ever wanted, it is an ordinary later migration that loses nothing but derived data. **Re-deriving everything** (for example after changing extraction rules): `UPDATE knowledge_document SET search_indexed_at = NULL` (SQLite: `knowledge_documents`); searches then re-index in bounded batches.

## 13. Known limitations and risks

- **Complexity budgets are conservative, not exhaustive.** A document over any budget — more than 4,000 `*`/`_`/`~`, 2,000 `]`, 500 underline-like lines or 4,000 list markers, counted anywhere including code, with container prefixes recognized after any indentation — is shown as plain text, with a notice. Indented code that merely looks like quotes, list items or underlines counts as if it were not code. The diagnostics cover the constructs measured above and budget-respecting fuzz; they are not a proof that no other construct is costly.
- **Search indexing writes during a search request**, including a viewer's. It changes only derived columns, is conditional, and is bounded to one batch (25 rows / 256 KiB); a large legacy project needs several searches (or Continue indexing) before search is complete, and says so until then.
- **Pending count is per project and approximate under concurrency**: rows another search has claimed but not yet committed are still counted as pending for that instant. The pending count and the result list are separate reads, not one snapshot; under concurrent writes by an older build they can disagree briefly. No linearizable guarantee is claimed.
- **Byte budget exception:** a single row larger than 256 KiB is still taken alone so indexing always progresses. Documents saved through the API are at most 50,000 characters and fit; an oversized historical or internally written row is the documented exception, not an absolute per-request byte ceiling.
- **PostgreSQL claimed-but-unselected rows:** the batch locks up to 25 candidates with `SKIP LOCKED` and may then select fewer because of the byte budget; the rest stay locked until the short transaction ends, which can briefly slow a concurrent search's progress (never duplicate work).
- **Case folding** is JavaScript `toLowerCase()` with NFC: no full Unicode case folding (`ß`/`SS`) and no locale rules (Turkish `İ`).
- `search_text` roughly doubles the storage of document text.
- No syntax highlighting and no heading IDs, so `#heading` links do not scroll (footnote anchors do).
- A mixed-version deployment (old and new builds writing at once) can leave a row stale until its next search, never wrong source.
- The accounts E2E suite's `next dev` server once failed to become ready within its 120 s window right after a source change; an unchanged rerun passed. Environmental, not caused by this release.
