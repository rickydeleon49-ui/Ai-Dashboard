# Design Note: Release 2C.2 — Assignment Experience

**Status:** Implemented (Stage 3E)

**Author:** AI-Dashboard Engineering Team

**Updated:** September 19, 2026

**Context:** Phase 2C (Team Collaboration), Release 2C.2 (ROADMAP §6)

---

## 1. User Outcome & Non-Goals

### User Outcome
In hosted accounts mode (`AUTH_MODE=accounts`), team members collaborating in a workspace need to assign tasks to active teammates, understand who made an assignment, inspect task assignees at a glance, and filter tasks across project views and **My Work** by assignment state ("Unassigned", "Assigned to me", "Assigned by me"). Historical task attribution must remain intact even when a former assignee is later suspended or removed from the workspace.

### Non-Goals for Release 2C.2
- **No Multi-Select Bulk Assignment:** Multi-select bulk task editing and bulk assignment belong to Release 2C.5 (Bulk editing); this release focuses strictly on single-task assignment in creation and editing flows.
- **No Full Activity Event Feed:** Full activity history, mentions, and the activity event stream belong to Release 2C.4 (Comments, mentions, and activity history). Release 2C.2 introduces the underlying provenance columns (`assigned_by`, `assigned_at`) so future activity streams can be backfilled and attributed reliably.
- **No Desktop Assignee Features:** Desktop mode remains a private, account-free, single-user SQLite environment. No assignee picker, member directory queries, or assignment filters are rendered on desktop.

## 2. Data Model & Additive PostgreSQL Migration

### Assignment Provenance Columns
To support "Assigned by me" filtering and audit provenance without depending on an unreleased activity subsystem, the `tasks` table in PostgreSQL introduces two additive columns:

1. **`assigned_by`**: `text REFERENCES "user"("id") ON DELETE SET NULL`
   - Records the user ID of the authenticated member who created or updated the assignment.
   - Nullable. If a task is unassigned or assigned prior to Release 2C.2, this is `NULL`.
2. **`assigned_at`**: `timestamp`
   - Records the timestamp when the current assignment was made.
   - Nullable. If a task is unassigned, this is `NULL`.

### Indexes
- An index on `(workspace_id, assigned_by)` (`task_workspace_assigned_by_idx`) ensures performant filtering for "Assigned by me" queries across all tasks in a workspace or project.

### Additive Migration 0012
- Migration file: `drizzle-pg/0012_task_assignment_provenance.sql`
- Registered in `drizzle-pg/meta/_journal.json` as index `12`.
- Verification test: the 0012 upgrade test is in `tests/unit-pg/migration-upgrade.test.ts`.
- SQL Statements:
```sql
ALTER TABLE "task" ADD COLUMN "assigned_by" text REFERENCES "user"("id") ON DELETE SET NULL;
ALTER TABLE "task" ADD COLUMN "assigned_at" timestamp;
CREATE INDEX "task_workspace_assigned_by_idx" ON "task" ("workspace_id", "assigned_by");
```

### Response Serialization
- `serializeTaskResponse()` in `src/core/tasks/serialize.ts` governs API output:
  - Accounts mode (`isAccountsMode()`): includes `assignedBy` and `assignedAt`.
  - Desktop mode: strips `assignedBy` and `assignedAt`, preserving the exact desktop API response shape.

## 3. Provenance Rules & Historical Assignees

### The Provenance-on-Change Rule
In `PostgresTaskRepository.update()`, assignment provenance (`assignee_id`, `assigned_by`, `assigned_at`) follows a strict change-detection policy:
1. **Unchanged Assignee (`input.assigneeId === existing.assigneeId`):**
   - No validation is run against the member directory.
   - Existing values of `assignee_id`, `assigned_by`, and `assigned_at` are preserved unmodified.
   - Non-assignment edits (e.g. updating task title, description, priority, or status) succeed even if the current historical assignee is now suspended or removed.
2. **Changed Assignee (different user ID):**
   - Validated against active workspace membership via `assertValidAssignee(tx, workspaceId, newAssigneeId)`.
   - `assigned_by` is set to `actorUserId`.
   - `assigned_at` is set to the current timestamp (`new Date()`).
3. **Cleared Assignee (`input.assigneeId === null`):**
   - All three fields are cleared: `assignee_id = NULL`, `assigned_by = NULL`, `assigned_at = NULL`.

### Historical Assignees (Suspended & Removed Members)
- Soft-removing (`status = 'removed'`) or suspending (`status = 'suspended'`) a workspace member leaves their user row intact. Historical tasks retain their foreign key link `task.assignee_id`.
- Read queries (`list`, `listForWorkspace`, `findById`) never reject or clear historical assignees.
- **Presentation Rules:**
  - Active: name and avatar/initials.
  - Suspended: name, avatar/initials, and explicit accessible indicator: `(Suspended)` with pause icon.
  - Removed: name, avatar/initials, and explicit accessible indicator: `(Former Member)` with distinct icon.
  - Status is never conveyed by color alone.
- **Picker Behavior:**
  - When editing a task with a historical suspended or removed assignee, the UI displays a clearly marked read-only chip showing their historical status.
  - The selectable dropdown list displays **active members only** plus **Unassigned**.
  - A suspended or removed member cannot be re-selected once changed.
  - Client defense-in-depth: the UI only sends `assigneeId` in PATCH payloads when the user has actually modified the assignment.
  - Search input is debounced by 300ms, and stale/out-of-order fetch responses are cancelled or ignored.

### The Display-Summary Rule (Privacy & Scoping)
To prevent leaking the workspace member directory or sensitive member details of suspended and former members to non-elevated users, task pages (`/projects/[id]/tasks` and `/my-work`) do not dump full member lists:
- Only user IDs actually referenced on the rendered tasks (deduplicated `assigneeId` and `assignedBy`) are queried via `getMemberDisplaySummaries(workspaceId, userIds, callerRole)`.
- Scoped strictly to `workspaceId` in SQL (`WHERE workspace_id = :workspaceId AND user_id = ANY(:userIds)`). Non-members return nothing.
- For `owner` and `admin`: returns the full safe summary (`{ id, name, email, image, role, status, joinedAt }`).
- For `member` and `viewer`: returns full summaries for `active` members only. For `suspended` and `removed` members, returns a minimal `{ id, name, status }`, strictly omitting `email`, `role`, and `joinedAt`.
- The Assignee Picker keeps loading active members on demand from `GET /api/workspaces/[id]/members?status=active`.

## 4. Authorization & Actor-Required Rule

### The Actor-Required Rule
- The repository interface `TaskRepository.create()` and `TaskRepository.update()` takes actor context via a clean options object: `{ actorUserId?: string }`.
- In `PostgresTaskRepository`, if an assignee is being set on creation or changed on update, and `options.actorUserId` is missing, an internal error (`Error("actorUserId is required when setting or changing an assignee")`) is thrown immediately rather than silently writing `assigned_by = NULL`.
- The task API routes (`POST /api/projects/:id/tasks`, `PATCH /api/tasks/:id`) always supply `{ actorUserId: session.userId }` derived server-side from the authenticated session.
- Request bodies are never permitted to supply `assignedBy`. Any client-supplied `assignedBy` in the payload is stripped/ignored, and `assigned_by` is always derived from the authenticated session user.

### Role Matrix
- **Owner, Admin, Member:** Authorized to create, edit, and assign tasks to any active workspace member.
- **Viewer:** Read-only access across projects and tasks. Viewers cannot create tasks, edit tasks, or assign tasks (server returns HTTP 403 `forbidden`).
  - In the UI, viewers see assignees read-only with no picker, disabled status toggles, and hidden create/edit/delete actions.
- **Outsider, Suspended, Removed:** Denied all workspace and task access (fail-closed HTTP 403 / 404).

### Hardening Invariants
1. **No Direct `invited → active` Transition:** `updateMember()` in `src/core/workspaces/service.ts` rejects any direct status update from `invited` to `active` with `InvalidMemberTransitionError` (HTTP 422). Invited members must only become active by accepting their invitation token.
2. **Mandatory `callerRole`:** `UpdateMemberOptions` and `RemoveMemberOptions` require `callerRole: WorkspaceRole`, ensuring permission checks cannot be bypassed by omission. Never spoof a `callerRole` (e.g. passing `"owner"` for non-owner callers).

## 5. Query Filters & API Contracts

### Extended Task Filters
Task list endpoints (`GET /api/projects/:id/tasks` and `GET /api/my-work`) and repository methods (`list`, `listForWorkspace`) support the following query filters:
1. **`unassigned` (boolean):** Matches tasks where `task.assignee_id IS NULL`.
2. **`assignedTo` (string):** Can be a specific member `userId` or `"me"`, which resolves server-side to the caller's session `userId`.
3. **`assignedBy` (string):** Can be a specific member `userId` or `"me"`, which resolves server-side to the caller's session `userId`.

### Query Validation
- Validated via Zod schemas (`taskQuerySchema` and `myWorkQuerySchema`). Invalid parameters return HTTP 422.
- `GET /api/my-work` in accounts mode defaults to "assigned to me" when no assignment filter is supplied, but cleanly allows "assigned by me", "unassigned", and "all" when specified.

### Member Summary Source for Assignee Picker
- The assignee picker fetches active members via `GET /api/workspaces/:id/members?status=active`.
- Returns `{ members: WorkspaceMemberSummary[], total }`. Safe user summary objects only, with zero private credential exposure.

## 6. Open Decisions from ROADMAP §20

1. **OPEN DECISION 1 — Activity Event Generation Timing:**
   - *Roadmap context:* ROADMAP §6 acceptance criteria specifies "Assignment changes generate activity events", while Release 2C.4 introduces the structured activity event and comment timeline.
   - *Options:*
     - Option A: Write minimal rows to the existing generic `activity_event` table now (`type = 'task.assigned'`).
     - Option B: Record durable provenance columns (`assigned_by`, `assigned_at`) on the task row now, and hook into the formal activity event subsystem in Release 2C.4 when activity schemas and notification models are unified.
   - *Status:* **OPEN**. For Release 2C.2, we implement Option B (provenance fields on the task row), ensuring zero unvalidated writes to the legacy activity table while capturing complete attribution data.

2. **OPEN DECISION 2 — Can viewers be assignees?**
   - *Roadmap context:* Today viewers are active workspace members and are assignable, but have read-only access and cannot update tasks (e.g. mark done or change status).
   - *Options:*
     - Option A: Keep viewers assignable. Useful for delegating reading, review, or oversight tasks where a viewer is responsible for reviewing material even if they do not update task progress directly in the dashboard.
     - Option B: Restrict assignees to `member`, `admin`, and `owner` only. Viewers would be excluded from the assignee picker and rejected with HTTP 422 if assigned.
   - *Status:* **OPEN**. Behavior remains unchanged in Release 2C.2 (viewers remain assignable). The user/stakeholder will decide whether to restrict assignee roles in a future iteration.

3. **OPEN DECISION 3 — Desktop Collaboration Synchronization:**
   - *Roadmap context:* §20 asks "Is desktop collaboration strictly single-user, or will local network/team synchronization eventually exist?"
   - *Decision:* Desktop remains strictly single-user with zero assignees in this release. No assignment or member schema changes are introduced in SQLite.
