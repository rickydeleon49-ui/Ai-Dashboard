# Design Note: Release 2C.2 — Assignment Experience

**Status:** Design & Specification (Stage 3A)  
**Author:** AI-Dashboard Engineering Team  
**Updated:** September 18, 2026  
**Context:** Phase 2C (Team Collaboration), Release 2C.2 (ROADMAP §6)  

---

## 1. User Outcome & Non-Goals

### User Outcome
In hosted accounts mode (`AUTH_MODE=accounts`), team members collaborating in a workspace need to assign tasks to active teammates, understand who made an assignment, inspect task assignees at a glance, and filter tasks across project views and **My Work** by assignment state ("Unassigned", "Assigned to me", "Assigned by me"). Historical task attribution must remain intact even when a former assignee is later suspended or removed from the workspace.

### Non-Goals for Release 2C.2
- **No Multi-Select Bulk Assignment:** Multi-select bulk task editing and bulk assignment belong to Release 2C.5 (Bulk editing); this release focuses strictly on single-task assignment in creation and editing flows.
- **No Full Activity Event Feed:** Full activity history, mentions, and the activity event stream belong to Release 2C.4 (Comments, mentions, and activity history). Release 2C.2 introduces the underlying provenance columns (`assigned_by`, `assigned_at`) so future activity streams can be backfilled and attributed reliably.
- **No Desktop Assignee Features:** Desktop mode remains a private, account-free, single-user SQLite environment. No assignee picker, member directory queries, or assignment filters are rendered on desktop.

## 2. Data Model & Additive PostgreSQL Migration

### Assignment Provenance Columns
To support "Assigned by me" filtering and audit provenance without depending on an unreleased activity subsystem, the `tasks` table in PostgreSQL requires two additive columns:

1. **`assigned_by`**: `text REFERENCES "user"("id") ON DELETE SET NULL`
   - Records the user ID of the authenticated member who created or updated the assignment.
   - Nullable. If a task is unassigned or assigned prior to Release 2C.2, this is `NULL`.
2. **`assigned_at`**: `timestamp with time zone` (or `timestamp` with `{ mode: "date" }`)
   - Records the timestamp when the current assignment was made.
   - Nullable. If a task is unassigned, this is `NULL`.

### Indexes
- An index on `(workspace_id, assigned_by)` ensures performant filtering for "Assigned by me" queries across all tasks in a workspace or project.

### Additive Migration Plan
- Migration file: `drizzle-pg/0012_task_assignment_provenance.sql`
- Registered in `drizzle-pg/meta/_journal.json` as index `12`.
- SQL Statements:
```sql
ALTER TABLE "task" ADD COLUMN "assigned_by" text REFERENCES "user"("id") ON DELETE SET NULL;
ALTER TABLE "task" ADD COLUMN "assigned_at" timestamp;
CREATE INDEX "task_workspace_assigned_by_idx" ON "task" ("workspace_id", "assigned_by");
```

### Invariant & Legacy Handling:
- Existing rows are backfilled as `NULL` for `assigned_by` and `assigned_at`.
- **"Assigned by me" filter behavior on legacy rows:** Queries for "Assigned by me" evaluate `task.assigned_by = $sessionUserId`. Tasks where `assigned_by IS NULL` are excluded from "Assigned by me" queries because their assigner cannot be reliably inferred.
- When an assignment is cleared (`assigneeId` set to `null`), `assigned_by` and `assigned_at` are reset to `NULL`.
- When an assignment is unchanged during a task edit (e.g., only `title` or `status` changes), existing `assigned_by` and `assigned_at` are preserved.

## 3. Historical Assignees: Suspended & Removed Members

### Invariant: Preserving Task Attribution
When a member is soft-removed (`status = 'removed'`) or suspended (`status = 'suspended'`), their user record and workspace membership record remain in the database (delivered in Release 2C.1).
- Foreign key constraints on `tasks.assignee_id` reference `users.id ON DELETE SET NULL`. Since soft-removal does not delete the `user` row, historical task records retain their `assignee_id`.
- The task repository's `assertValidAssignee` check runs only during **mutations** that create or change `assigneeId`. Read queries (`list`, `listForWorkspace`, `findById`) do not reject or clear historical assignees.

### Presentation Rules:
1. **Active Assignee:** Display user name, avatar/initials.
2. **Suspended Assignee:** Display user name, avatar/initials with an accessible indicator/badge: `(Suspended)`.
3. **Removed (Former) Member:** Display user name, avatar/initials with an accessible indicator/badge: `(Former Member)`.
4. **Deleted User Account:** If an account was deleted via GDPR hard delete (`assignee_id` set to `null` by cascade), the task renders as "Unassigned".

### Picker Rules:
- When opening the assignee picker for a task with a historical suspended/removed assignee:
  - The picker displays the current assignee as a read-only, clearly labeled chip.
  - The searchable dropdown list contains **only active members**.
  - A user cannot re-select or re-assign a suspended or removed member.
  - Selecting an active member or choosing "Unassigned" replaces the historical assignee.

## 4. Authorization & Invariants

### Who Can Assign
- **Owner & Admin (Active):** Full permission to create, edit, and assign tasks to any active workspace member.
- **Member (Active):** Standard collaborator; can create, edit, and assign tasks to any active workspace member (including self or teammates).
- **Viewer (Active):** Viewers have read-only permissions across projects and tasks. Viewers **cannot** create tasks, edit tasks, or assign tasks (server returns HTTP 403 `forbidden`).
- **Suspended / Removed / Outsider:** Denied all task operations (HTTP 403 `inactive_member` or `not_a_member`).

### Assignee Validation Invariant:
Every task assignment (POST / PATCH) is strictly validated server-side by `assertValidAssignee(tx, workspaceId, assigneeId)`:
- `assigneeId` must correspond to a row in `workspace_member` with `workspace_id = :workspaceId` AND `status = 'active'`.
- Assigning an outsider user ID fails with HTTP 422 (`InvalidAssigneeError`).
- Assigning an invited user (not yet accepted) fails with HTTP 422 (`InvalidAssigneeError`).
- Assigning a suspended user fails with HTTP 422 (`InvalidAssigneeError`).
- Assigning a removed member fails with HTTP 422 (`InvalidAssigneeError`).
- Assigning `null` or unassigned is always allowed for members, admins, and owners.

### Actor Derivation (Never Trust Client-Supplied Assigner):
- The API routes never accept an `assignedBy` field from the client body.
- When `assigneeId` changes or is set on creation, `assigned_by` is always derived directly from the authenticated session (`session.userId`).

## 5. Query Filters & API Contracts

### Extended Task Filters
Task list endpoints (`GET /api/projects/:id/tasks` and `GET /api/my-work`) and repository methods (`list`, `listForWorkspace`) support the following assignment filters:

1. **`unassigned` (boolean):**
   - When `true`, matches tasks where `task.assignee_id IS NULL`.
2. **`assignedTo` (string):**
   - Can be `"me"` (resolves to authenticated user's ID) or a specific member `userId`.
   - SQL condition: `task.assignee_id = :targetUserId AND task.workspace_id = :workspaceId`.
3. **`assignedBy` (string):**
   - Can be `"me"` (resolves to authenticated user's ID) or a specific member `userId`.
   - SQL condition: `task.assigned_by = :targetUserId AND task.workspace_id = :workspaceId`.

### Member Summary Source for Assignee Picker
- The assignee picker requires a list of active members in the workspace.
- The existing endpoint `GET /api/workspaces/:id/members?status=active` (shipped in 2C.1) returns `{ members: WorkspaceMemberSummary[], total }`.
- Viewers, Members, Admins, and Owners are all authorized to call `GET /api/workspaces/:id/members?status=active`.
- The returned `WorkspaceMemberSummary` contains only safe fields (`id`, `name`, `email`, `image`, `role`, `status`), with zero secret exposure.

## 6. Open Decisions from ROADMAP §20

1. **OPEN DECISION 1 — Activity Event Generation Timing:**
   - *Roadmap context:* ROADMAP §6 acceptance criteria specifies "Assignment changes generate activity events", while Release 2C.4 introduces the structured activity event and comment timeline.
   - *Options:*
     - Option A: Write minimal rows to the existing generic `activity_event` table now (`type = 'task.assigned'`).
     - Option B: Record durable provenance columns (`assigned_by`, `assigned_at`) on the task row now, and hook into the formal activity event subsystem in Release 2C.4 when activity schemas and notification models are unified.
   - *Status:* **OPEN**. For Release 2C.2, we implement Option B (provenance fields on the task row), ensuring zero unvalidated writes to the legacy activity table while capturing complete attribution data.

2. **OPEN DECISION 2 — Desktop Collaboration Synchronization:**
   - *Roadmap context:* §20 asks "Is desktop collaboration strictly single-user, or will local network/team synchronization eventually exist?"
   - *Decision:* Desktop remains strictly single-user with zero assignees in this release. No assignment or member schema changes are introduced in SQLite.
