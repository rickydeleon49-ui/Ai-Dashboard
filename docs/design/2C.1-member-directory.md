## 1. User Outcome & Non-Goals

### User Outcome
In hosted accounts mode (`AUTH_MODE=accounts`), workspace collaborators need to see who belongs to their workspace, understand their roles, and find teammates by name or email. This release introduces a secure, paginated, and searchable workspace member directory backed by an explicit membership status lifecycle (`active`, `invited`, `suspended`, `removed`).

### Non-Goals for Release 2C.1
- **No Invitations UI:** Creation, acceptance, revocation, or email delivery of workspace invitations is out of scope for this release (scheduled for Phase 4A; underlying database invitations table already exists from Phase 2).
- **No Assignee Picker UI:** The frontend member-backed assignee picker and bulk assignment interactions are out of scope (scheduled for Release 2C.2).
- **No API Routes or UI in Step 1:** Step 1 delivers only the design note, database migration, domain types, service/repository query layer, and task assignee validation. API routes and frontend presentation follow in Steps 2 and 3 after architectural review.

## 2. Membership State Model & Additive Migration

### State Definitions
A member's lifecycle within a workspace is modeled by a `status` column:

1. **`active`**:
   - The member is in good standing.
   - Can access the workspace and collaborate.
   - Can be assigned new tasks.
   - Displayed in standard member directory queries.
2. **`invited`**:
   - An invitation was created for the user or email, but full activation/acceptance is pending.
   - Cannot be assigned new tasks until active.
3. **`suspended`**:
   - The member's access is temporarily revoked by an administrator or owner.
   - Retains past contributions, task history, and comment attribution.
   - Cannot log in or perform actions within this workspace.
   - **Cannot be assigned new tasks.**
4. **`removed`**:
   - The member has been removed from the workspace.
   - Preserves historical records (past task assignments, comments, audit activity).
   - Denied access to the workspace.
   - **Cannot be assigned new tasks.**

### Additive Migration Plan
Per ROADMAP §2 and §14, database evolution must be strictly additive, zero-downtime, and backward-compatible:
- File: `drizzle-pg/0009_workspace_member_status.sql`
- Add column `status` of type `text` to `workspace_member`, with `NOT NULL DEFAULT 'active'`.
- Backfill existing rows: `UPDATE "workspace_member" SET "status" = 'active' WHERE "status" IS NULL;`.
- Add check constraint: `CHECK ("status" in ('active', 'invited', 'suspended', 'removed'))`.
- Journal: Recorded as entry `9` in `drizzle-pg/meta/_journal.json`.
- Invariant: Existing rows remain completely valid and default to `'active'`. Nothing is renamed or dropped.

## 3. "Removed" Status vs. Existing `removeMember()` Hard Deletes

### Background
Currently, `removeMember(workspaceId, userId)` executes a hard delete:
```sql
DELETE FROM workspace_member WHERE workspace_id = $1 AND user_id = $2;
```
Meanwhile, task assignment history references `user(id) ON DELETE SET NULL`. If a member row is hard-deleted:
1. Historical task records retain `task.assignee_id = userId`, but cannot distinguish between a user who was previously a workspace collaborator versus an outsider who never belonged to the workspace.
2. Subsequent task updates or re-validations could fail if code checks whether `assigneeId` is currently present in `workspace_member`.
3. Account deletion and ownership transfer triggers (`workspace_member_last_owner`) enforce that the last owner of a workspace cannot be removed.

### DECISION 1 (RESOLVED — Option A: Dual Lifecycle / Soft-Removal Default)
- `removeMember(workspaceId, userId)` sets `status = 'removed'` while keeping the membership row. Historical task attribution and member creation timestamps are preserved.
- Hard deletion (`DELETE FROM workspace_member`) is reserved for explicit account deletion cascade or GDPR right-to-be-forgotten purges.
- **Re-invitation & Reactivation:** When a removed user is re-invited and accepts an invitation, `acceptInvitation()` locks the existing row (`SELECT ... FOR UPDATE`) and reactivates it (`status = 'active'`, `role = invitation.role`, `invitedBy = invitation.invitedBy`). Original `createdAt` is retained (`joinedAt` represents first join date).
- **Suspension Protection:** A suspended member cannot be re-invited (`createInvitation()` rejects with `membership_suspended`) and cannot rejoin via invitation (`acceptInvitation()` rejects with `membership_suspended`). Only a workspace admin or owner can reinstate them (`updateMemberStatus()`).
- **Direct Invited Status Guard:** The `invited` status cannot be set directly through `updateMemberStatus()`; only the invitation flow creates or transitions it.

## 4. Authorization Matrix: Directory Access & Administration

### Active Status Requirement
Only members with `status = 'active'` pass authorization. Any membership row with `status` other than `'active'` (`'suspended'`, `'removed'`, or `'invited'`) is rejected by `requireRole()` with an `inactive_member` error (HTTP 403) across all role levels.

| Role / Identity | Read Member Directory | Update Role / Status | Notes |
| :--- | :---: | :---: | :--- |
| **Owner (Active)** | Allowed | Allowed | Full control; cannot demote or remove the last active owner (enforced by DB trigger). |
| **Admin (Active)** | Allowed | Allowed (Scoped) | Can update members and viewers; cannot demote or remove owners; cannot promote to owner. |
| **Member (Active)** | Allowed | Denied (403) | Standard collaborator; can view directory to collaborate and assign teammates. |
| **Viewer (Active)** | Allowed | Denied (403) | Read-only collaborator; can view directory to see team composition and task assignees. |
| **Suspended / Removed** | Denied (403) | Denied (403) | Inactive status rejects all workspace actions with HTTP 403 `inactive_member`. |
| **Outsider** | Denied (403/404) | Denied (403/404) | Cross-workspace isolation enforced at repository and query level (`not_a_member`). |
| **Unauthenticated** | Denied (401) | Denied (401) | Session required in hosted accounts mode. |

### DECISION 2 (RESOLVED — Option A: Viewers Can Read the Member Directory)
- Viewers have read-only access to projects, tasks, and the member directory.
- **Directory Visibility Rules:** Non-admin members and viewers only see members with `status = 'active'`. Owners and admins can inspect and filter by any status (`active`, `invited`, `suspended`, `removed`, or `all`).
- Default status filter is `active` for all callers. When a non-admin explicitly requests a non-active status, the server returns HTTP 403.

## 5. Safe User-Summary Shape

To satisfy ROADMAP §14 (Security: prevent secret exposure) and Release 2C.1 acceptance criteria, member queries must return a strictly defined, safe shape.

### TypeScript Interface
```typescript
export interface WorkspaceMemberSummary {
  id: string;
  name: string | null;
  email: string | null;
  image: string | null;
  role: WorkspaceRole;
  status: WorkspaceMemberStatus;
  joinedAt: Date;
}
```

### Prohibited Fields (Never Returned)
- Authentication secrets or credentials (the system uses magic links and does not store passwords in user records)
- OAuth accounts and provider tokens (`account.*`)
- Sessions and session tokens (`session.*`)
- Email verification internals (`emailVerified`)
- Memberships or roles in other workspaces (cross-tenant leakage)

## 6. API Contract (Planned for Step 2)

### Endpoint
`GET /api/workspaces/:workspaceId/members`

### Query Parameters
- `limit`: optional integer, default `20`, minimum `1`, maximum `100` (server-enforced max page size).
- `offset`: optional integer, default `0`, minimum `0`.
- `search`: optional string. Searches case-insensitively across `users.name` and `users.email` with literal wildcard escaping.
- `status`: optional string filter (`active`, `invited`, `suspended`, `removed`, or omitted for all).

### Response Envelope
```json
{
  "members": [
    {
      "id": "usr_123",
      "name": "Alex Smith",
      "email": "alex@example.com",
      "image": "https://...",
      "role": "member",
      "status": "active",
      "joinedAt": "2026-09-18T12:00:00.000Z"
    }
  ],
  "total": 42,
  "limit": 20,
  "offset": 0
}
```

## 7. Desktop Behavior

- Desktop mode is active when neither `AUTH_MODE=accounts`, `DATABASE_URL`, nor `DASHBOARD_PASSWORD` are configured (see `src/lib/auth-mode.ts`). In this mode, Command Center operates as a single-user local application using SQLite (`data/dashboard.db`).
- There are no user accounts, sessions, or multi-tenant workspace members in desktop mode.
- The member directory is an accounts-mode capability.
- In desktop mode, desktop users never require an account, never hit the PostgreSQL member directory, and task assignees default to unassigned / local user without schema friction.
