# Design Note: Release 2C.6 — Collaboration Notifications

**Status:** Implemented on `phase2c/collaboration-notifications`, uncommitted, awaiting independent review

**Updated:** September 21, 2026

**Context:** Phase 2C (Team Collaboration), Release 2C.6 (ROADMAP §6)

---

## 1. User outcome and non-goals

### User outcome

In hosted accounts mode (`AUTH_MODE=accounts`), a workspace member learns, inside the product, when a teammate:

- assigns them a task, or takes a task away from them
- mentions them in a task comment
- comments on a task they are assigned to
- sets, changes, or clears the due date on a task they are assigned to

Each member has a per-workspace inbox with read/unread state, archive/restore, mark-all-read, a workspace-specific unread count, paginated history, and per-category preferences.

### Non-goals (explicit)

- **No email, push, or any external delivery.** No transport, no provider, no outbound network call.
- **No scheduled due-date reminders** ("due tomorrow", "overdue"). These need a durable scheduler and belong to Phase 2F. This release adds **no polling loop, timer, or recurring job**. Due-date notifications are generated synchronously, inside the request that changed the date (§6.4).
- **No real-time push.** The unread count refreshes on page load, when the window regains focus, after the user's own inbox actions, and when the panel opens.
- **No digests or batching.**
- **No notifications for comment edits or deletions.** An edit that adds a mention does not notify, so an edit can't be used to ping people repeatedly. A later release can add this with a per-mention idempotency key.
- **No notifications for status, priority, milestone, dependency, or checklist changes.** These remain visible in the 2C.4 activity timeline.
- **No desktop notifications.** See §9.

### Naming: "inbox", not "notifications"

`/notifications` and `/api/notifications` already exist. They are the desktop automation inbox, backed by an unscoped SQLite table, and `proxy.ts` blocks them in accounts mode. Collaboration notifications therefore use a separate namespace, `/inbox` and `/api/inbox`, so the two can never share a route, a table, or a code path. The SQLite automation inbox is untouched.

## 3. Data model (PostgreSQL only)

Additive migration `drizzle-pg/0015_collaboration_notifications.sql` creates two new tables. It touches no existing table, rewrites no data, and edits no released migration.

### `notification`

| Column | Type | Notes |
|---|---|---|
| `id` | text PK | `gen_random_uuid()::text` |
| `workspace_id` | text NOT NULL → `workspace.id` **ON DELETE CASCADE** | tenant boundary |
| `recipient_id` | text NOT NULL → `user.id` **ON DELETE CASCADE** | owner of the row |
| `actor_id` | text → `user.id` ON DELETE SET NULL | who caused it |
| `category` | text NOT NULL, CHECK in (`assignment`, `mention`, `comment`, `due_date`) | |
| `source_event_id` | text NOT NULL | id of the `task_activity_event` that produced it; **no FK**, so the notification survives task deletion |
| `task_id` | text → `task.id` ON DELETE SET NULL | |
| `project_id` | text → `project.id` ON DELETE SET NULL | |
| `comment_id` | text → `task_comment.id` ON DELETE SET NULL | |
| `details` | jsonb NOT NULL DEFAULT `{}` | allowlisted, non-content fields only (§5) |
| `read_at` | timestamp | null = unread |
| `archived_at` | timestamp | null = in inbox |
| `created_at` | timestamp NOT NULL | database clock, millisecond precision (§7) |

Constraints and indexes:

- `notification_recipient_source_uq` UNIQUE (`recipient_id`, `source_event_id`): the idempotency constraint (§6.6)
- `notification_inbox_idx` (`recipient_id`, `workspace_id`, `created_at` DESC, `id` DESC): every list query and cursor seek
- `notification_unread_idx` (`recipient_id`, `workspace_id`) WHERE `read_at IS NULL AND archived_at IS NULL`: the unread count
- `notification_workspace_idx` (`workspace_id`): supports the workspace-delete cascade
- Partial indexes on `task_id`, `project_id`, `comment_id`, `actor_id` (each `WHERE … IS NOT NULL`), so `ON DELETE SET NULL` never sequentially scans the table

**Why SET NULL for targets:** deleting a task, project, or comment must not rewrite a user's history into a silent gap. The row stays, and the UI says the item is no longer available (§8.4). Deleting a workspace or a user account removes that workspace's or that user's notifications entirely.

### `notification_preference`

| Column | Type |
|---|---|
| `workspace_id` | text NOT NULL → `workspace.id` ON DELETE CASCADE |
| `user_id` | text NOT NULL → `user.id` ON DELETE CASCADE |
| `category` | text NOT NULL, CHECK in the four categories |
| `enabled` | boolean NOT NULL |
| `updated_at` | timestamp NOT NULL |

PK (`workspace_id`, `user_id`, `category`). There is one row per category, not a JSON blob. A partial update therefore writes only the rows it names and cannot reset another category, even under concurrent requests (§10).

### Desktop (SQLite)

No SQLite migration. Desktop deliberately omits the feature (§9), so SQLite has nothing to store.

## 4. Security model

### 4.1 Tenant boundary

Every row carries `workspace_id` and `recipient_id`. **Every repository method takes both as mandatory arguments and filters on both in SQL**, including the single-row update, which uses `WHERE id = $id AND workspace_id = $ws AND recipient_id = $me`. There's no method that looks a notification up by ID alone. A foreign or unknown ID matches zero rows and is indistinguishable from a missing one.

Joins used to render a notification are also scoped: `task.workspace_id = notification.workspace_id`, and the same for project, comment, and the actor's membership. A notification can never render another workspace's task title, even if a row were somehow corrupted.

### 4.2 Recipient validity

Recipients are never trusted from the client:

- **Assignment/due-date recipients** come from the task row itself: the assignee the server just wrote, or the one it replaced. The assignee is already validated as an active member (`assertValidAssignee`).
- **Mention recipients** come from the existing `validateMentions()` resolution in the comment repository, which extracts IDs server-side, bounds them (≤ 50, UUID format), and checks workspace membership.
- **Comment recipients** come from the task's current assignee, read inside the comment's transaction.

The insert itself then re-filters every recipient against `workspace_member` for **the same workspace with `status = 'active'`**. Invited, suspended, and removed members, outsiders, and users from other workspaces produce no row, whatever the caller passed.

### 4.3 Content safety

Notification rows store identifiers and a small allowlisted `details` object. They never store:

- comment bodies or excerpts
- task titles or descriptions
- file contents
- authentication data, or anything from the request body beyond validated IDs and dates

Task and project names are read live, at render time, through workspace-scoped joins. A rename is reflected, and nothing user-authored is duplicated into the notification table. On output, `details` passes through a second allowlist (`sanitizeNotificationDetails`), which drops unknown keys and non-conforming values. All text renders as React text nodes. There's no `dangerouslySetInnerHTML`.

### 4.4 Deleted-comment privacy (consistent with 2C.4)

For `mention` and `comment` notifications, the actor is shown **only if the comment is still live**. If it was soft-deleted or no longer exists, the response has `actor: null` and `comment.deleted: true`. This matches 2C.4's rule that a deleted comment must not keep revealing who wrote it.

### 4.5 Actor display

For other categories, the actor's display name is shown only while the actor still has a `workspace_member` row in that workspace (any status, the same visibility 2C.1 gives members for historical attribution). Only `id` and `name` are returned, never email.

## 6. Notification generation

### 6.1 Principle: same transaction, after the write

Notifications are inserted **inside the same database transaction as the underlying change**, immediately after its activity event, by `insertNotificationDrafts(tx, drafts)`. Consequences:

- A failed operation creates no notification, because the transaction rolls back.
- A successful operation cannot commit without its notifications, so nothing is lost between the two.
- A notification write that fails (a database error, never a duplicate) rolls back the operation. This coupling is deliberate: a partially notified change is worse than a retryable failure. A duplicate is not an error (§6.6).

### 6.2 Trigger matrix

| Operation | Condition | Recipient | Category | Source event |
|---|---|---|---|---|
| Create task (`POST /api/projects/:id/tasks`) | assignee set | assignee | `assignment` (`assigned`) | `task.created` |
| Update task (`PATCH /api/tasks/:id`, bulk) | assignee changed to a user | new assignee | `assignment` (`assigned`) | `task.assigned` |
| Update task | assignee changed away from a user | previous assignee | `assignment` (`unassigned`) | `task.assigned` / `task.unassigned` |
| Update task | due date's **calendar date** changed (set, moved, or cleared) | resulting assignee, unless they receive an `assigned` notification from the same update | `due_date` | `task.dates_changed` |
| Create comment | valid mentions | each mentioned user | `mention` | `comment.created` |
| Create comment | task has an assignee | assignee | `comment` — unless a `mention` for them was already created from the same comment (§6.8) | `comment.created` |

The same rules run for single-task updates and for bulk editing, because bulk editing calls `updateAuthoritative` once per task. A bulk item that fails, or reports `unchanged`, never reaches the generation code, so notifications are generated only for successful, materially changed tasks.

### 6.3 No-op updates

Generation is keyed off the same conditions that emit activity events. A no-op update (same assignee, same calendar date) emits no activity event and therefore no notification. The no-op check runs under the task's `FOR UPDATE` row lock, so two identical concurrent updates produce exactly one change and one notification.

### 6.4 "Due-date events", resolved

The roadmap's "due-date events" is ambiguous. This release chooses **synchronous change notifications**: the assignee is told when the task's due date is set, moved to a different calendar day, or cleared. A change within the same calendar day, such as a time component, is not material and is ignored, matching the activity log's `task.dates_changed` rule. "Due soon" and "overdue" reminders are **not** implemented, because they need a scheduler (Phase 2F).

### 6.5 Self-notification policy

A user is **never** notified about their own action: `recipient_id IS DISTINCT FROM actor_id` in the insert. Assigning yourself, commenting on your own task, and mentioning yourself all produce nothing. No exception was found useful enough to justify noise.

### 6.6 Idempotency and duplicate suppression

Every notification is derived from exactly one activity event, and `(recipient_id, source_event_id)` is UNIQUE. The insert uses `ON CONFLICT DO NOTHING`, so:

- processing the same event twice, whether by retrying the writer or by concurrent duplicate processing, yields one row per recipient
- a recipient who is both mentioned and assigned receives exactly one notification, never two (§6.8).

**Request-level retries:** a retried task update is a no-op the second time (§6.3), so nothing is duplicated. A retried `POST /comments` creates a second comment. That's pre-existing 2C.4 behavior, and it correctly yields a second notification for a genuinely new comment. Request idempotency keys for comment creation are listed as an open decision (§13).

### 6.7 Preference enforcement

The insert excludes recipients who have an `enabled = false` row for that workspace and category (`NOT EXISTS`). The preference is checked **in the database, in the same statement that creates the row**, not in the UI.

### 6.8 A mentioned assignee: precedence, with fallback

When a comment both mentions the task's assignee and is a comment on their task, they qualify for two categories at once. The rule is **mention takes precedence, and `comment` is the fallback when the mention is suppressed**:

| Their `mention` preference | Their `comment` preference | Result |
|---|---|---|
| on | on | exactly one `mention` |
| on | off | exactly one `mention` |
| off | on | exactly one `comment` |
| off | off | nothing |

**How it is enforced.** The assignee stays in **both** drafts. Nothing is filtered in application code; the database decides:

1. The `mention` draft is inserted **first**. If mentions are enabled, the row is created.
2. The `comment` draft is inserted second, with the assignee still in its recipient list. Because both drafts carry the same `source_event_id`, the `(recipient_id, source_event_id)` unique constraint makes that insert a no-op — the mention already occupies the pair.
3. If mentions are **disabled**, step 1 inserts nothing (the preference filter removed them), so step 2's insert succeeds and they get the `comment` notification instead.
4. If both are disabled, both statements filter them out and they get nothing.

Removing the assignee from the comment draft when they were mentioned — filtering *before* preferences are evaluated — would break row 3 of the table: someone who had only mentions turned off would silently receive nothing. Ordering plus the unique constraint is what keeps exactly one row in every combination, including under concurrency (§10).

Self-notification is unaffected: the actor is excluded from every draft by `recipient_id IS DISTINCT FROM actor_id`, so a comment author who mentions themself on their own task still receives nothing, whatever their preferences say.

## 7. Lifecycle, ordering, and pagination

- **Timestamps:** `created_at`, `read_at`, and `archived_at` come from `date_trunc('milliseconds', statement_timestamp() AT TIME ZONE 'UTC')`, the same database-clock rule as 2C.4 comments. There's one clock across instances, and millisecond precision survives the JavaScript `Date` round trip exactly.
- **Order:** `created_at DESC, id DESC`. `id` is the unique tiebreaker, so the order is total and deterministic even when many rows share a millisecond. Bulk editing and multi-mention comments routinely create such ties.
- **Cursor:** opaque base64url JSON `{ createdAt, id }`. Decoding is strict: at most 512 characters, base64url charset only, a JSON object with exactly those two keys, a canonical ISO-8601 millisecond timestamp, and a UUID `id`. Anything else is a 400. The seek predicate is `(created_at, id) < (cursor.createdAt, cursor.id)`. Rows are never skipped or repeated across pages, including across timestamp ties and while other rows change read state.
- **Page size:** default 20, maximum 50.
- **Views:** `view=inbox` (not archived, the default) or `view=archived`; `filter=all` (default) or `filter=unread`.
- **Read/unread:** marking read sets `read_at = COALESCE(read_at, now)`, which is idempotent and keeps the first read time. Marking unread clears it.
- **Archive/restore:** archiving sets `archived_at = COALESCE(archived_at, now)`; restoring clears it. Archiving does not change read state.
- **Unread count:** unread and not archived, for the authenticated recipient in the active workspace only.
- **Mark all read:** one `UPDATE … WHERE workspace_id = $ws AND recipient_id = $me AND read_at IS NULL`, covering the inbox and archived rows of that workspace alone. Notifications committed after the statement's snapshot stay unread.

## 8. API contracts

All routes are accounts-mode only. `proxy.ts` allows `/api/inbox` and `/inbox` in accounts mode. Outside accounts mode every `/api/inbox` route returns **404** before touching any database, and `/inbox` renders not-found. Every response is `Cache-Control: no-store`.

| Method & path | Body / query | Success |
|---|---|---|
| `GET /api/inbox` | `view`, `filter`, `limit`, `cursor` | `200 { workspaceId, notifications, nextCursor, unreadCount }` |
| `GET /api/inbox/unread-count` | — | `200 { workspaceId, unreadCount }` |
| `PATCH /api/inbox/:id` | `{ read?: boolean, archived?: boolean }`, at least one, strict | `200 { workspaceId, notification, unreadCount }` |
| `POST /api/inbox/mark-all-read` | — | `200 { workspaceId, updated, unreadCount }` |
| `GET /api/inbox/preferences` | — | `200 { workspaceId, preferences }` |
| `PATCH /api/inbox/preferences` | partial `{ assignment?, mention?, comment?, due_date? }` booleans, strict, at least one | `200 { workspaceId, preferences }` |

`workspaceId` in every response lets the client discard a response that arrived after a workspace switch.

### 8.1 Notification representation

```json
{
  "id": "uuid",
  "category": "assignment",
  "read": false,
  "readAt": null,
  "archived": false,
  "archivedAt": null,
  "createdAt": "2026-09-21T18:00:00.000Z",
  "actor": { "id": "user-id", "name": "Alice" },
  "task": { "id": "tsk_…", "title": "Ship it", "projectId": "prj_…" },
  "project": { "id": "prj_…", "name": "Launch" },
  "comment": { "id": "uuid", "deleted": false },
  "details": { "change": "assigned" }
}
```

`task`, `project`, `comment`, and `actor` are `null` when the target no longer exists in the workspace or must be withheld (§4.4, §4.5).

### 8.2 Errors

| Condition | Status |
|---|---|
| Not accounts mode | 404 `Not found.` |
| No session | 401 |
| Cookie names a workspace where the caller is suspended/removed | 403 |
| Not an active member of the resolved workspace | 403 |
| Malformed query, cursor, or body; unknown field; unknown category; non-boolean | 400 |
| Unknown, malformed, or foreign notification ID | 404 `Notification not found.` (identical for all three) |

## 9. Desktop behavior: deliberately omitted

Desktop mode is single-user and account-free. Assignees don't exist there, and 2C.4 mentions return 422, so every trigger in §6.2 either can't happen or would notify the only user about their own action, which §6.5 forbids. Desktop therefore has **no collaboration notifications**:

- no SQLite table or migration; SQLite repositories are unchanged
- `/api/inbox/**` returns 404 outside accounts mode, before resolving a workspace or opening a database
- `/inbox` renders not-found outside accounts mode
- the header shows the existing SQLite automation bell on desktop, exactly as before, and the collaboration inbox button only in accounts mode
- the generation hooks live only in the PostgreSQL repositories, which desktop never loads

Accounts mode, in turn, never reaches SQLite notification storage. The collaboration inbox is PostgreSQL-only by construction, and the accounts-mode no-SQLite regression test now also invokes every `/api/inbox` route.

## 10. Concurrency semantics (PostgreSQL)

| Scenario | Guarantee | Mechanism |
|---|---|---|
| The same event processed twice concurrently | one row per recipient | unique `(recipient_id, source_event_id)` + `ON CONFLICT DO NOTHING` |
| Identical concurrent assignments | one change, one notification | task row `FOR UPDATE` + no-op detection |
| Concurrent read + archive on one row | both applied; final state read **and** archived | each is a single-row `UPDATE` touching only its own column, serialized by the row lock |
| Concurrent read + unread | last committer wins; row is consistent | single-row `UPDATE` |
| Mark-all-read in workspace A vs. rows in workspace B | B untouched | predicate includes `workspace_id` and `recipient_id` |
| Concurrent preference updates to different categories | both persist | one row per category; `INSERT … ON CONFLICT DO UPDATE` names only the provided categories |
| Concurrent updates to the same category | one row; last committer wins | PK on (`workspace_id`, `user_id`, `category`) |
| Preference change racing notification creation | a preference committed before the generating statement starts is honored; a later one is not retroactive; existing notifications are never deleted by a preference change | single `INSERT … SELECT … WHERE NOT EXISTS (disabled pref)` statement under READ COMMITTED |
| Suspension racing notification creation | a suspension committed before the generating statement excludes the user; a row created just before a suspension stays stored, but the suspended user can't read it (every route requires active membership) | membership filter in the same statement |

## 11. Authorization matrix (accounts mode)

Notifications are personal. Any **active** member (`viewer` and above) may read and manage **their own** notifications and preferences in their current workspace. No route accepts a recipient or user ID. The recipient is always the session user.

| Caller | All `/api/inbox` routes |
|---|---|
| Owner / Admin / Member / Viewer (active) | allowed, own rows only |
| Suspended / Removed | 403 |
| Outsider (no membership) | resolves to their own workspace; can never see this workspace's rows |
| Unauthenticated | 401 |
| Anyone, a foreign notification ID | 404 |

Generation follows the existing mutation policy. Only callers who may already assign, edit due dates (`member`+), or comment (`member`+) can cause notifications, and only for active members of the same workspace.

## 12. User interface and accessibility

- **Header button** (accounts mode only): a bell button labelled "Notifications, N unread" or "Notifications, no unread". A numeric badge shows the count as text, not just a colored dot. `aria-haspopup="dialog"` and `aria-expanded` are set.
- **Panel:** a dialog listing the ten most recent inbox notifications, with "Mark all read" and "Open inbox". Escape closes it and returns focus to the bell, and clicking outside closes it.
- **Inbox page** (`/inbox`): Inbox/Archived views, an All/Unread filter (toggle buttons with `aria-pressed`), "Load more" pagination, and category preferences (labelled checkboxes with a polite status message).
- **Each item:** unread items show a visible "Unread" label and bold text, not only a color change. The action buttons (Mark read/unread, Archive/Restore) have accessible names that include what they act on.
- **States:** loading (`aria-busy` plus text), empty ("You're all caught up" / "No archived notifications"), error (`role="alert"` with Retry), and pagination ("Load more" / end of list).
- **Links:** the task link goes to `/projects/:projectId/tasks#task-:taskId` only while the task still exists in the workspace. Otherwise the item says "This task is no longer available". A deleted comment shows "Comment deleted" and hides the actor.
- **Workspace switching:** the layout keys the inbox button and the inbox page by the resolved workspace ID, so switching workspaces remounts them and drops all cached state. Every response also carries `workspaceId`, and a client discards any response for a workspace other than the one it was mounted for. That covers a request in flight during the switch.

## 13. Known limitations and open decisions

- **Comment request idempotency:** a retried `POST /api/tasks/:id/comments` creates a second comment and a second notification (§6.6). An `Idempotency-Key` header is a candidate for a later release.
- **Comment recipients:** comment notifications go to the task's assignee only, not to previous commenters. "Thread participants" is a possible extension.
- **Generation/operation coupling:** a database failure in notification insertion rolls back the underlying operation (§6.1). The alternative, a savepoint that lets the operation commit without notifications, was rejected as silent loss.
- **Retention:** notifications are kept until their workspace or recipient is deleted. There's no automatic pruning, which would need Phase 2F jobs.
- **Suspension race:** see §10. A notification stored for a user suspended a moment later stays in the table, but it's unreadable while they're suspended and visible again only if they're reinstated.
